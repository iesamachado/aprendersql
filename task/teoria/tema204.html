1. Triggers (Disparadores): Concepto, Momentos y Eventos

Un Trigger (o disparador) es un bloque de código SQL almacenado en el motor de la base de datos que se ejecuta automáticamente de forma reactiva cuando ocurre una operación de manipulación de datos (INSERT, UPDATE o DELETE) sobre una tabla determinada.

Idea fundamental: A diferencia de una función o un procedimiento almacenado ordinario, un trigger nunca se llama de forma manual (no existe un CALL mi_trigger()). Se dispara por sí solo en el servidor cuando se produce el evento para el que fue programado.

¿Para qué se utilizan en Administración de BBDD?

Auditoría y Trazabilidad

Registrar quién (USER()), cuándo (NOW()) y qué modificó en tablas críticas (salarios, contraseñas, emails o estados de pedidos).

Integridad y Restricciones

Validar reglas de negocio avanzadas que una simple CHECK no puede comprobar, o impedir borrados accidentales abortando la transacción con errores personalizados.

Cálculos y Sincronización

Recalcular totales, aplicar tarifas según códigos postales, descontar stock en almacén o actualizar saldos de forma desatendida.

Los Dos Componentes del Disparo: Momento y Acción

Para configurar cualquier trigger en MariaDB debemos responder a dos preguntas esenciales:

1. Momento de Disparo: BEFORE vs AFTER
  • BEFORE

    Se ejecuta antes de que la modificación se aplique físicamente a la tabla o se validen restricciones de integridad.
    Ideal para: Validar datos, modificar o sanitizar valores entrantes (modificando NEW.columna), o cancelar la instrucción antes de que toque la tabla.

  • AFTER

    Se ejecuta después de que la fila ha sido guardada/actualizada/eliminada satisfactoriamente.
    Ideal para: Operaciones en otras tablas, como alimentar tablas de auditoría histórica, descontar inventario en almacén o actualizar acumulados.

2. Operación DML Disparadora
  • INSERT Se activa cuando entra una nueva fila (INSERT INTO ...).
  • UPDATE Se activa cuando cambia algún dato en una fila ya existente (UPDATE ...).
  • DELETE Se activa cuando una fila va a desaparecer (DELETE FROM ...).
Esto produce un total de 6 combinaciones posibles por tabla: BEFORE INSERT, AFTER INSERT, BEFORE UPDATE, AFTER UPDATE, BEFORE DELETE y AFTER DELETE.

Sintaxis Estándar y el uso de DELIMITER en MariaDB

Dado que el cuerpo del trigger contendrá varias sentencias finalizadas con punto y coma (;), es imprescindible cambiar temporalmente el delimitador de sentencias del cliente con DELIMITER:

DELIMITER //

CREATE TRIGGER nombre_del_trigger
{ BEFORE | AFTER } { INSERT | UPDATE | DELETE }
ON nombre_tabla
FOR EACH ROW
BEGIN
    -- Bloque de instrucciones SQL
    -- Condiciones IF, bucles, asignaciones o llamadas a procedimientos
END //

DELIMITER ;
Granularidad: ¿Por qué siempre FOR EACH ROW?
En MariaDB, los triggers se ejecutan a nivel de fila (Row-Level Triggers). Si una única sentencia UPDATE clientes SET estado = 'Inactivo' WHERE ciudad = 'Granada'; actualiza 40 registros, el trigger se ejecutará 40 veces independientes, una por cada fila afectada.

Administración de Triggers en el Servidor

-- Listar todos los triggers de la base de datos actual
SHOW TRIGGERS;

-- Listar los triggers asociados a una tabla concreta
SHOW TRIGGERS LIKE 'pedidos';

-- Consultar metadatos avanzados desde el diccionario del sistema
SELECT TRIGGER_NAME, EVENT_MANIPULATION, EVENT_OBJECT_TABLE, ACTION_TIMING, CREATED
FROM information_schema.TRIGGERS
WHERE TRIGGER_SCHEMA = DATABASE();

-- Eliminar un trigger existente
DROP TRIGGER IF EXISTS trg_auditar_pedidos;

2. Las Pseudotablas NEW y OLD en Detalle

Dentro del cuerpo de un trigger no podemos saber "mágicamente" qué fila se está tocando usando un SELECT corriente. Para ello, MariaDB proporciona dos pseudorregistros especiales: NEW y OLD.

Estas variables tienen exactamente los mismos campos y tipos de datos que la tabla que dispara el evento. Para acceder a sus columnas se usa la sintaxis de punto: NEW.nombre_columna y OLD.nombre_columna.

Evento DML Pseudotabla OLD (Valores Anteriores) Pseudotabla NEW (Valores Nuevos) ¿Permite modificación con SET?
INSERT No disponible (es NULL) Contiene los datos de la nueva fila que se va a insertar. Sí Sólo en BEFORE INSERT (ej: SET NEW.fecha = NOW();)
UPDATE Contiene los datos originales antes de modificarse. Contiene los datos entrantes propuestos por el usuario. Sí Sólo en BEFORE UPDATE (ej: SET NEW.descuento = 10;)
DELETE Contiene los datos de la fila justo antes de ser eliminada. No disponible (la fila deja de existir) No No tiene sentido asignar valores a una fila que va a desaparecer.
Detección de Cambios Reales en UPDATE

Cuando un usuario ejecuta un UPDATE, muchas veces las columnas no cambian realmente su contenido. Para no registrar auditorías vacías o no gastar CPU innecesariamente, filtramos con un condicional:

IF OLD.salario <> NEW.salario THEN
    -- El salario ha cambiado de verdad
    -- Ejecutamos la auditoría o la lógica
END IF;
¡La Trampa de MariaDB! Error 1442 (Tabla Mutante)

El error más común de los alumnos: En un trigger de la tabla pedidos intentan hacer:

UPDATE pedidos SET total = 100 WHERE id = NEW.id;

MariaDB lo rechazará con: ERROR 1442: Can't update table 'pedidos' in stored function/trigger because it is already used by statement...
Solución correcta: Haz el trigger BEFORE y modifica la columna directamente con:
SET NEW.total = 100; (¡Sin lanzar ningún UPDATE!).

3. Metodología Pautada: De Procedure a Trigger (Paso a Paso)

Programar triggers directamente suele ser frustrante para los estudiantes: como saltan de fondo de forma implícita, si hay un fallo sintáctico, de tipos o un cálculo erróneo, la consola de MariaDB solo muestra un error opaco al hacer el INSERT o UPDATE.

La Filosofía Didáctica: Separar la Lógica del Disparo

Para construir triggers sin perdernos, dividimos siempre el problema en dos fases estructuradas:
1. Crear y probar un Stored Procedure con toda la lógica de negocio pura y dura, probándolo manualmente en la consola con CALL.
2. Crear el Trigger como una "fina capa reactiva" que solo se encarga de extraer los datos de NEW u OLD y llamar al Procedure.

FASE 1: El Stored Procedure (La Lógica)

En el procedimiento almacenado nos centramos exclusivamente en resolver el problema algorítmico:

  1. Parámetros de entrada: Definir qué datos necesita recibir mediante parámetros IN (IDs, importes, cantidades).
  2. Variables locales: Declarar variables internas con DECLARE y volcar datos de consultas con SELECT columna INTO v_variable FROM ....
  3. Cálculos y validaciones: Realizar operaciones matemáticas, aplicar descuentos o evaluar condiciones lógicas con IF ... THEN ... ELSE.
  4. Modificación de tablas: Ejecutar el UPDATE, INSERT INTO historico o lanzar un error de interrupción con SIGNAL.
Prueba Unitaria: Ejecutamos CALL sp_logica(1, 50); en el terminal y comprobamos con un SELECT que la base de datos reacciona como queremos.
FASE 2: El Trigger (El Cableado Reactivo)

Una vez que el procedure funciona a la perfección, crear el trigger es coser y cantar:

  1. Decidir el Disparador:
    • ¿Qué tabla lo dispara?
    • ¿Qué acción: INSERT, UPDATE o DELETE?
    • ¿Qué momento: BEFORE o AFTER?
  2. Obtener los datos de entrada: Extraer exactamente los parámetros que el procedure exige leyendo los campos de NEW (en inserciones/actualizaciones) o de OLD (en borrados).
  3. Invocar el Procedure: Escribir una única línea limpia dentro del trigger: CALL sp_logica(NEW.id, NEW.importe);
Resultado: Si el trigger falla, sabemos exactamente si el error es de sintaxis del evento o de la lógica interna del procedure.
2 Reglas de Oro de MariaDB al llamar Procedures desde Triggers:
  • Prohibido devolver Result Sets directos: El procedure invocado por un trigger NO puede hacer un SELECT columna FROM ... simple a pantalla sin cláusula INTO. Los triggers son silenciosos y no admiten devolver resultados interactivos al cliente.
  • Prohibido el control explícito de transacciones: El procedure no puede contener sentencias COMMIT ni ROLLBACK. La transacción la gobierna la instrucción SQL original que disparó el evento.

4. Catálogo de Ejemplos en MariaDB

A continuación repasamos los 4 casos de uso más importantes en MariaDB, aplicando la metodología pautada y los diferentes momentos de disparo.

Ejemplo 1: Metodología Pautada (Descuento de Stock al Vender) AFTER INSERT + PROCEDURE

Escenario: Cada vez que se añade una línea de venta en lineas_pedido(id, pedido_id, producto_id, cantidad), debemos descontar automáticamente esa cantidad del stock en la tabla productos(id, nombre, stock). Si no hay suficiente stock, impedimos la venta.

Paso 1: Programar el Stored Procedure con la lógica
DELIMITER //

CREATE OR REPLACE PROCEDURE sp_descontar_stock(
    IN p_producto_id INT,
    IN p_cantidad INT
)
BEGIN
    -- 1. Declarar variables locales
    DECLARE v_stock_actual INT DEFAULT 0;

    -- 2. Obtener el stock actual del producto mediante SELECT INTO
    SELECT stock INTO v_stock_actual
    FROM productos
    WHERE id = p_producto_id;

    -- 3. Comprobaciones lógicas y cálculos
    IF v_stock_actual IS NULL THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Error: El producto especificado no existe en el catálogo.';
    ELSEIF v_stock_actual < p_cantidad THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Error: Stock insuficiente para completar la venta.';
    ELSE
        -- 4. Modificar la tabla destino
        UPDATE productos
        SET stock = stock - p_cantidad
        WHERE id = p_producto_id;
    END IF;
END //

DELIMITER ;
Probando el procedure de forma aislada:
Podemos ejecutar CALL sp_descontar_stock(1, 2); para comprobar que resta 2 unidades del producto 1 sin necesidad de disparar nada todavía.
Paso 2: Conectar el Trigger reactivo

Decidimos: Momento AFTER (porque la línea ya debe estar registrada), Evento INSERT, Tabla lineas_pedido. Extraemos NEW.producto_id y NEW.cantidad:

DELIMITER //

CREATE OR REPLACE TRIGGER trg_descontar_stock_venta
AFTER INSERT ON lineas_pedido
FOR EACH ROW
BEGIN
    -- Llamamos directamente al procedure con los datos entrantes de la pseudotabla NEW
    CALL sp_descontar_stock(NEW.producto_id, NEW.cantidad);
END //

DELIMITER ;
Ejemplo 2: Auditoría y Trazabilidad Histórica AFTER UPDATE (OLD vs NEW)

Escenario: En la tabla jugadores(id, nombre, puntos) queremos registrar en una tabla histórica cada vez que se modifican los puntos de un jugador, guardando los puntos antiguos, los nuevos, la fecha exacta y el usuario de base de datos que ejecutó la orden.

-- 1. Tabla para almacenar el histórico
CREATE TABLE IF NOT EXISTS historico_puntos (
    id INT AUTO_INCREMENT PRIMARY KEY,
    jugador_id INT NOT NULL,
    puntos_antiguos INT NOT NULL,
    puntos_nuevos INT NOT NULL,
    fecha_modificacion DATETIME DEFAULT NOW(),
    usuario_bd VARCHAR(80) NOT NULL
);

-- 2. Trigger de auditoría reactivo
DELIMITER //

CREATE OR REPLACE TRIGGER trg_auditar_puntos_jugador
AFTER UPDATE ON jugadores
FOR EACH ROW
BEGIN
    -- Comparamos si el valor de la columna ha cambiado realmente
    IF OLD.puntos <> NEW.puntos THEN
        INSERT INTO historico_puntos (
            jugador_id,
            puntos_antiguos,
            puntos_nuevos,
            fecha_modificacion,
            usuario_bd
        ) VALUES (
            NEW.id,
            OLD.puntos,
            NEW.puntos,
            NOW(),
            USER()
        );
    END IF;
END //

DELIMITER ;
Ejemplo 3: Seguridad Anti-Desastres (Bloqueo de Borrado) BEFORE DELETE + SIGNAL

Escenario: En la tabla pedidos(id, cliente_id, estado, total) debemos impedir terminantemente que cualquier usuario o script borre pedidos que ya figuren como 'Pagado' o 'Entregado'. Si alguien lo intenta, abortamos con un mensaje de error personalizado.

DELIMITER //

CREATE OR REPLACE TRIGGER trg_proteger_pedidos_facturados
BEFORE DELETE ON pedidos
FOR EACH ROW
BEGIN
    -- En un DELETE consultamos la fila que se va a borrar a través de OLD
    IF OLD.estado IN ('Pagado', 'Entregado') THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'ACCESO DENEGADO: No está permitido borrar pedidos facturados o entregados.';
    END IF;
END //

DELIMITER ;
El código de estado SQLSTATE '45000' es el estándar SQL para definir una excepción no controlada definida por el usuario.
Ejemplo 4: Cálculo Automático e Interceptación de Valores BEFORE UPDATE (SET NEW.campo)

Escenario: En la tabla pedidos(id, cp, gastos_envio), si se modifica el Código Postal (cp), el sistema debe recalcular los gastos de envío automáticamente antes de persistir los cambios en disco. Recuerda que no podemos hacer UPDATE pedidos para no provocar el Error 1442.

DELIMITER //

CREATE OR REPLACE TRIGGER trg_recalcular_gastos_envio
BEFORE UPDATE ON pedidos
FOR EACH ROW
BEGIN
    -- Verificamos si el código postal ha cambiado
    IF OLD.cp <> NEW.cp THEN
        -- Interceptamos el nuevo valor antes de que se grabe en disco
        IF NEW.cp LIKE '18%' THEN
            SET NEW.gastos_envio = 0.00; -- Envío local gratuito (ej. Granada)
        ELSEIF NEW.cp LIKE '28%' OR NEW.cp LIKE '08%' THEN
            SET NEW.gastos_envio = 4.95; -- Tarifa peninsular reducida (Madrid / Barcelona)
        ELSE
            SET NEW.gastos_envio = 8.50; -- Tarifa estándar
        END IF;
    END IF;
END //

DELIMITER ;

5. Cursores (Iteración Registro a Registro)

Las bases de datos relacionales trabajan por defecto de forma masiva sobre conjuntos de datos. Sin embargo, cuando se requiere una lógica compleja que necesita evaluar una fila a la vez, se utilizan Cursores dentro de un Procedimiento Almacenado.

Los 4 Pasos Obligatorios para Usar un Cursor

  1. Declaración: DECLARE nombre_cursor CURSOR FOR consulta_select; (Debe ir después de declarar las variables corrientes).
  2. Apertura: OPEN nombre_cursor; (Ejecuta internamente la consulta y sitúa el puntero al inicio).
  3. Lectura (Fetch): FETCH nombre_cursor INTO var1, var2; (Copia los datos de la fila actual a variables locales y avanza a la siguiente).
  4. Cierre: CLOSE nombre_cursor; (Libera la memoria del servidor).

Ejemplo Completo con Loop y Handler de Fin

DELIMITER //

CREATE OR REPLACE PROCEDURE procesar_empleados()
BEGIN
    DECLARE done INT DEFAULT FALSE;
    DECLARE var_id INT;
    DECLARE var_nombre VARCHAR(100);
    
    -- 1. Declarar cursor
    DECLARE cursor_empleados CURSOR FOR 
        SELECT id, nombre FROM empleados;
    
    -- Manejador de fin de cursor: cuando FETCH no encuentre más filas, done pasa a TRUE
    DECLARE CONTINUE HANDLER FOR NOT FOUND SET done = TRUE;

    -- 2. Abrir cursor
    OPEN cursor_empleados;

    read_loop: LOOP
        -- 3. Leer la fila actual
        FETCH cursor_empleados INTO var_id, var_nombre;
        
        -- Si ya no quedan registros, salimos del bucle
        IF done THEN
            LEAVE read_loop;
        END IF;
        
        -- Procesamiento individual de cada empleado (ej. cálculos, inserciones)
    END LOOP;

    -- 4. Cerrar cursor
    CLOSE cursor_empleados;
END //

DELIMITER ;

6. Excepciones y Handlers (Manejo de Errores)

En MariaDB, el control de errores dentro de procedimientos y triggers se realiza mediante HANDLERS (manejadores). Permiten interceptar fallos como claves primarias duplicadas, valores nulos o desconexiones, evitando que el script aborte inesperadamente.

Sintaxis de Handlers

DECLARE { CONTINUE | EXIT } HANDLER FOR { condición_error }
BEGIN
    -- Instrucciones a ejecutar al ocurrir la excepción
END;
Acción del Handler
  • CONTINUE

    Ejecuta el bloque del manejador y continúa con la siguiente instrucción que seguía a la sentencia que falló.

  • EXIT

    Ejecuta el bloque del manejador y termina inmediatamente la ejecución del bloque BEGIN...END actual.

Condiciones de Error Comunes
  • SQLEXCEPTION: Atrapa cualquier error estándar SQL (códigos de error que no sean advertencias o fin de datos).
  • SQLWARNING: Atrapa avisos o warnings generados por el motor.
  • NOT FOUND: Usado típicamente en cursores cuando FETCH ya no devuelve más filas.
  • Código de error numérico: Por ejemplo, 1062 (clave primaria o índice único duplicado).

7. Eventos Programados (Event Scheduler)

Los eventos (Events) son tareas temporales que el servidor de MariaDB ejecuta de forma desatendida en un momento futuro o con una periodicidad establecida (el equivalente a los cron jobs de Linux dentro del motor de base de datos).

Prerrequisito imprescindible: Para que los eventos se ejecuten, el planificador debe estar encendido en la configuración o en la sesión del servidor: SET GLOBAL event_scheduler = ON;

Sintaxis Básica de Creación

CREATE EVENT nombre_evento
ON SCHEDULE { AT timestamp | EVERY intervalo [STARTS timestamp] [ENDS timestamp] }
DO
BEGIN
    -- Sentencias SQL a ejecutar de forma automática
END;
Evento Único (AT)

Se ejecuta una única vez en un momento exacto del futuro.

CREATE EVENT cerrar_promocion
ON SCHEDULE AT CURRENT_TIMESTAMP + INTERVAL 1 DAY
DO
    UPDATE ofertas SET activa = FALSE WHERE id = 12;
Evento Recurrente (EVERY)

Se repite periódicamente a intervalos constantes.

CREATE EVENT depurar_logs_antiguos
ON SCHEDULE EVERY 1 WEEK
DO
    DELETE FROM auditoria 
    WHERE fecha < NOW() - INTERVAL 6 MONTH;
