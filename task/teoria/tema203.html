1. La Filosofía de la Seguridad: "Ser Rancios" y Principio de Mínimo Privilegio

En administración de bases de datos, la seguridad descansa sobre una máxima pedagógica irrenunciable: "Ser rancios". El administrador de sistemas gestores no debe regalar permisos por comodidad; debe ser extremadamente tacaño y riguroso.

Principio de Mínimo Privilegio

Cada usuario, rol o aplicación informática debe operar con el conjunto estrictamente mínimo e indispensable de privilegios para cumplir su función, y solo durante el tiempo necesario. Si una app web solo necesita leer platos, jamás debe tener permisos de UPDATE, DROP o administración global.

Defensa en Profundidad

La seguridad no depende de una única barrera. Se articula en múltiples capas superpuestas: cortafuegos de red, cifrado en tránsito (TLS/SSL), control de acceso a nivel de gestor, aislamiento por usuarios, roles, vistas y restricciones lógicas.

Regla de oro: Jamás utilices la cuenta root para la conexión de aplicaciones backend (PHP, Python, Java, etc.) ni para tareas operativas cotidianas. Si la aplicación sufre una vulnerabilidad de Inyección SQL (SQLi), el atacante obtendría el control total del servidor de base de datos.

2. Gestión de Usuarios, Hosts y Autenticación

En MariaDB y MySQL, la identidad de una cuenta de usuario no es solo un nombre, sino una tupla compuesta por 'usuario'@'host'. Un mismo nombre de usuario puede tener contraseñas, permisos y orígenes totalmente independientes según el host desde el que se conecte.

Host Especificado Significado y Ámbito de Conexión Nivel de Seguridad
'usuario'@'localhost' Solo permite conexiones locales desde la propia máquina que aloja la base de datos (mediante socket UNIX / plugin unix_socket o loopback 127.0.0.1). Máximo Recomendado para administradores locales.
'usuario'@'%' Comodín que permite conexiones desde cualquier dirección IP o máquina remota del mundo. Riesgo Alto Exige contraseñas muy robustas y cifrado.
'usuario'@'192.168.1.%' Permite conexiones únicamente desde máquinas pertenecientes a esa subred IP privada específica. Equilibrado Ideal para servidores web o VPNs corporativas.
'usuario'@'servidor-web.dominio.es' Restringe el acceso al Fully Qualified Domain Name (FQDN) indicado (resolución inversa DNS). Específico Requiere resolución DNS fiable.

Comandos de Gestión de Cuentas

-- 1. Crear cuentas de usuario
CREATE USER 'camarero1'@'%' IDENTIFIED BY 'ClaveRobusta2024!';
CREATE USER 'admin_tienda'@'192.168.1.%' IDENTIFIED BY 'AdminPass*987';
CREATE USER 'script_backup'@'localhost' IDENTIFIED BY 'BackupLocalSeguro#1';

-- 2. Modificar contraseñas y atributos de una cuenta existente
ALTER USER 'camarero1'@'%' IDENTIFIED BY 'NuevaClaveSegura2025$';

-- 3. Bloquear y desbloquear una cuenta (suspensión temporal)
ALTER USER 'camarero1'@'%' ACCOUNT LOCK;
ALTER USER 'camarero1'@'%' ACCOUNT UNLOCK;

-- 4. Exigir conexión cifrada obligatoria con TLS/SSL
ALTER USER 'admin_tienda'@'192.168.1.%' REQUIRE SSL;

-- 5. Forzar la caducidad de contraseña en el próximo inicio de sesión
ALTER USER 'camarero1'@'%' PASSWORD EXPIRE;

-- 6. Renombrar una cuenta de usuario manteniendo sus privilegios
RENAME USER 'camarero1'@'%' TO 'camarero_principal'@'%';

-- 7. Eliminar definitivamente una cuenta
DROP USER IF EXISTS 'empleado_baja'@'%';

-- 8. Consultar cuentas de usuario registradas en el diccionario del sistema
SELECT User, Host, plugin, authentication_string, account_locked 
FROM mysql.user;

-- 9. Verificar la identidad de la sesión activa
SELECT USER();         -- Devuelve la identidad que el cliente solicitó (ej. 'camarero'@'192.168.1.50')
SELECT CURRENT_USER(); -- Devuelve la cuenta autenticada según las reglas de privilegios (ej. 'camarero'@'%')
Plugins de Autenticación: MariaDB y MySQL utilizan plugins de autenticación para almacenar los hashes de las claves. Los más destacados son mysql_native_password (clásico SHA-1), caching_sha2_password (SHA-256 de alta seguridad por defecto en MySQL 8) y ed25519 en MariaDB.

3. Catálogo Completo de Privilegios (DML, DDL y Administrativos)

MariaDB clasifica sus privilegios en tres grandes categorías según la naturaleza de las operaciones que autorizan:

Privilegios DML (Datos)

Autorizan la lectura y manipulación de las filas de las tablas:

  • SELECT: Consultar registros.
  • INSERT: Añadir nuevas filas.
  • UPDATE: Modificar datos existentes.
  • DELETE: Borrar filas de tablas (no borra estructuras).
  • EXECUTE: Ejecutar rutinas (procedimientos y funciones).
Privilegios DDL (Estructura)

Autorizan la definición y alteración de objetos de la base de datos:

  • CREATE: Crear nuevas bases de datos o tablas.
  • ALTER: Modificar estructura (columnas, tipos).
  • DROP: Destruir bases de datos, tablas o vistas completas.
  • INDEX: Crear y eliminar índices sobre columnas.
  • CREATE VIEW / SHOW VIEW: Gestionar e inspeccionar vistas.
  • CREATE ROUTINE / ALTER ROUTINE: Crear y modificar procedimientos y funciones.
  • TRIGGER / EVENT: Crear disparadores y eventos.
Privilegios Administrativos

Autorizan operaciones sobre el motor, hilos, archivos y seguridad global:

  • ALL PRIVILEGES: Todos los privilegios disponibles.
  • PROCESS: Ver todas las consultas de todos los usuarios con SHOW PROCESSLIST.
  • RELOAD: Recargar privilegios y logs (FLUSH).
  • SHUTDOWN: Apagar el servidor MariaDB.
  • SUPER: Modificar variables globales, matar hilos ajenos con KILL y gestionar replicación.
  • FILE: Leer/escribir archivos en el SO del host (LOAD DATA INFILE, INTO OUTFILE).
  • CREATE USER: Administrar cuentas de usuario.
  • GRANT OPTION: Delegar permisos a otros.
  • SHOW DATABASES: Listar todas las bases de datos.
  • LOCK TABLES: Bloquear tablas explícitamente (LOCK TABLES tabla READ/WRITE y UNLOCK TABLES).
Distinción vital: DELETE vs DROP
El privilegio DELETE solo autoriza a borrar filas de datos con DELETE FROM tabla WHERE ...; no permite destruir la estructura de la tabla. Para destruir o eliminar una tabla o base de datos entera con DROP TABLE o DROP DATABASE es imprescindible el privilegio DROP.
Riesgo crítico del privilegio FILE:
El privilegio FILE opera a nivel global del servidor. Si se concede a un usuario no confiable, este podría leer ficheros sensibles del sistema operativo del servidor (ej. /etc/passwd) mediante LOAD DATA INFILE o escribir puertas traseras o shells web en directorios accesibles mediante SELECT ... INTO OUTFILE. Por ello, solo debe reservarse estrictamente a administradores.

4. Niveles de Granularidad (Global, BD, Tabla, Columna y Rutina)

MariaDB permite otorgar privilegios con una granularidad milimétrica. La sintaxis de la cláusula ON determina el nivel de alcance del privilegio:

Nivel Sintaxis en GRANT / REVOKE Tabla del Sistema en mysql.* Ejemplo Típico
Global ON *.* mysql.user GRANT RELOAD, PROCESS ON *.* TO 'admin'@'localhost';
Base de Datos ON nombre_bd.* mysql.db GRANT SELECT, INSERT ON arepazo.* TO 'gestor'@'%';
Tabla ON nombre_bd.nombre_tabla mysql.tables_priv GRANT SELECT, UPDATE ON arepazo.pedidos TO 'cocina'@'%';
Columna GRANT SELECT (c1, c2), UPDATE (c1) ON bd.tabla mysql.columns_priv GRANT SELECT (id, nombre, email) ON arepazo.empleados TO 'recepcion'@'%';
Procedimiento / Rutina ON PROCEDURE bd.procedimiento mysql.procs_priv GRANT EXECUTE ON PROCEDURE arepazo.sp_cierre_caja TO 'cajero'@'%';

5. Asignación y Revocación de Privilegios (GRANT, REVOKE y Diagnóstico)

Los privilegios se conceden mediante GRANT y se retiran mediante REVOKE.

Sintaxis de GRANT

GRANT privilegio1, privilegio2
ON [nivel]
TO 'usuario'@'host' [IDENTIFIED BY 'contraseña']
[WITH GRANT OPTION];
La Cláusula WITH GRANT OPTION:
Permite al usuario receptor conceder a otros usuarios los mismos privilegios que él posee sobre ese objeto. Debe manejarse con extrema precaución: si un usuario con WITH GRANT OPTION es comprometido, un atacante podría escalar privilegios y crear nuevos usuarios con accesos no autorizados.

Sintaxis de REVOKE

-- Revocar un privilegio específico sobre una base de datos
REVOKE DELETE ON arepazo.* FROM 'camarero1'@'%';

-- Revocar el permiso de delegación WITH GRANT OPTION
REVOKE GRANT OPTION ON arepazo.* FROM 'gestor'@'%';

-- Revocar TODOS los privilegios que posee un usuario
REVOKE ALL PRIVILEGES, GRANT OPTION FROM 'usuario_temporal'@'%';

Inspección de Privilegios

-- Consultar los permisos concedidos al usuario actual conectado
SHOW GRANTS;

-- Consultar los permisos de una cuenta específica
SHOW GRANTS FOR 'camarero1'@'%';
¿Cuándo usar FLUSH PRIVILEGES?

MariaDB mantiene las tablas de permisos cacheadas en memoria. Cuando ejecutas comandos estándar como GRANT, REVOKE o CREATE USER, MariaDB actualiza la memoria automáticamente; FLUSH PRIVILEGES no es necesario.

Solo es obligatorio ejecutar FLUSH PRIVILEGES; si un administrador modifica directamente las tablas del sistema con sentencias manuales INSERT, UPDATE o DELETE sobre mysql.user o mysql.db.

Diagnóstico de Errores: "Access Denied"

Si un usuario recibe el error:
ERROR 1045 (28000): Access denied for user 'ana'@'192.168.1.45' (using password: YES)

Las tres causas más frecuentes son:
1. La contraseña introducida es incorrecta.
2. La cuenta 'ana' existe solo para 'ana'@'localhost' pero se está conectando desde una IP remota.
3. No se ha otorgado ningún privilegio de acceso ni conexión para ese host.

6. Roles: Agrupación y Centralización de Permisos (Modelo RBAC)

Un Rol es un contenedor con nombre que agrupa un conjunto de privilegios. Este enfoque implementa el modelo estándar de la industria RBAC (Role-Based Access Control). En lugar de conceder 15 permisos a cada uno de los 50 camareros de una empresa, creamos el rol rol_camarero, le asignamos los permisos una sola vez y otorgamos el rol a los empleados. Esto aplica el principio DRY (Don't Repeat Yourself) a la administración de seguridad.

Paso 1: Crear y Configurar el Rol
-- 1. Crear el rol
CREATE ROLE 'rol_cocinero';
CREATE ROLE 'rol_camarero';

-- 2. Asignar privilegios al rol
GRANT SELECT, UPDATE ON arepazo.pedidos TO 'rol_cocinero';
GRANT SELECT, INSERT ON arepazo.lineas_pedido TO 'rol_camarero';

-- 3. Eliminar un rol si ya no es necesario
DROP ROLE IF EXISTS 'rol_temporal';
Paso 2: Asignar el Rol al Usuario
-- Conceder el rol a uno o varios usuarios
GRANT 'rol_cocinero' TO 'carlos'@'%';
GRANT 'rol_camarero' TO 'lucia'@'%';

-- Delegar la administración del rol (permite asignarlo a otros)
GRANT 'rol_cocinero' TO 'jefe_cocina'@'%' WITH ADMIN OPTION;

-- Revocar el rol de un usuario
REVOKE 'rol_camarero' FROM 'lucia'@'%';

Activación de Roles en Sesión

En MariaDB, cuando un usuario inicia sesión, sus roles asignados no están activos por defecto a menos que se configure explícitamente. El usuario o el administrador controlan la activación: 

-- Activar un rol específico en la sesión actual
SET ROLE 'rol_cocinero';

-- Activar TODOS los roles asignados al usuario
SET ROLE ALL;

-- Desactivar todos los roles activos (volver a los permisos base del usuario)
SET ROLE NONE;

-- Consultar qué rol se encuentra actualmente activo en la sesión
SELECT CURRENT_ROLE();

-- Configurar un rol predeterminado para que se active automáticamente al conectar
SET DEFAULT ROLE 'rol_cocinero' FOR 'carlos'@'%';
SET DEFAULT ROLE ALL FOR 'lucia'@'%';

-- Consultar roles asignados y disponibles en el diccionario del sistema
SELECT * FROM information_schema.APPLICABLE_ROLES;
SELECT * FROM information_schema.ENABLED_ROLES;

7. Vistas (Views) como Barrera de Seguridad

Las Vistas son consultas almacenadas con nombre que actúan como tablas virtuales. En seguridad, constituyen una de las herramientas más elegantes para implementar control de acceso granular sin alterar la estructura física de las tablas:

Seguridad a Nivel de Columna

Permiten ocultar columnas sensibles (DNI, salarios, contraseñas) proyectando solo los datos públicos:

CREATE VIEW vista_empleados_publico AS
SELECT id, nombre, apellidos, departamento, extension_telefonica
FROM empleados;
-- (Se ocultan: salario_base, cuenta_bancaria, dni)
Seguridad a Nivel de Fila (RLS)

Añadiendo una cláusula WHERE, restringimos qué registros son visibles según el departamento o sucursal:

CREATE VIEW vista_pedidos_madrid AS
SELECT * FROM pedidos 
WHERE sucursal_id = 1;

Desacoplamiento Total de la Tabla Base

El mayor beneficio de seguridad es que podemos otorgar permisos GRANT SELECT al usuario exclusivamente sobre la vista, sin darle ningún permiso sobre la tabla subyacente. El usuario podrá consultar la vista con normalidad y el motor resolverá los datos de forma transparente. 

-- Conceder acceso a la vista sin tocar la tabla empleados original
GRANT SELECT ON arepazo.vista_empleados_publico TO 'recepcion'@'%';
La Cláusula WITH CHECK OPTION

Si una vista es actualizable y permite operaciones INSERT o UPDATE, un usuario podría introducir datos que contradigan el filtro WHERE de la vista (por ejemplo, insertar un pedido de Barcelona a través de la vista de Madrid).

Añadir WITH CHECK OPTION al final de la vista obliga a que cualquier modificación cumpla estrictamente la condición del WHERE; en caso contrario, MariaDB aborta la operación con un error: 

-- Modificar o recrear una vista existente de forma atómica
CREATE OR REPLACE VIEW vista_platos_disponibles AS
SELECT id, nombre, precio, disponible
FROM platos
WHERE disponible = 1
WITH CHECK OPTION;

-- Si alguien intenta ejecutar:
-- UPDATE vista_platos_disponibles SET disponible = 0 WHERE id = 5;
-- MariaDB lo RECHAZARÁ inmediatamente con ERROR 1369 (CHECK OPTION failed).

-- Consultar metadatos y código de las vistas en el diccionario del sistema
SELECT TABLE_NAME, VIEW_DEFINITION FROM information_schema.VIEWS WHERE TABLE_SCHEMA = 'arepazo';
DEFINER vs INVOKER: En MariaDB, una vista con SQL SECURITY DEFINER (por defecto) se ejecuta con los privilegios del usuario que creó la vista; con SQL SECURITY INVOKER, se evalúan en cada consulta los permisos del usuario que la está ejecutando.
Cumplimiento del RGPD: Las vistas son una herramienta clave para el cumplimiento del Reglamento General de Protección de Datos (RGPD), ya que permiten aplicar la minimización de datos y ocultar o anonimizar información sensible (DNI, salarios, datos bancarios) según el rol laboral.

8. Sinónimos (Synonyms) y Abstracción de Esquemas

Introducidos en MariaDB 10.5+ (mediante compatibilidad con sintaxis Oracle), los Sinónimos son alias oficiales asignados a tablas, vistas u otros objetos de la base de datos.

Abstracción y Ocultación

Permiten ocultar el nombre técnico real de tablas críticas o la estructura interna de esquemas antiguos (ej. tab_emp_v3_2024_final expuesta simplemente como empleados).

Portabilidad

Facilitan la migración entre entornos sin tener que reescribir consultas en el código de las aplicaciones, redirigiendo el sinónimo hacia la nueva tabla.

Sinónimos Públicos vs Privados

Un sinónimo privado pertenece a un esquema concreto, mientras que un PUBLIC SYNONYM es accesible globalmente por todos los usuarios sin prefijar el esquema. 

-- Crear un sinónimo privado para una tabla (MariaDB 10.5+)
CREATE SYNONYM menu_platos FOR arepazo_prod.tbl_catalogo_platos_interna;

-- Crear un sinónimo público accesible por todos los usuarios (entornos Oracle / extensiones)
CREATE PUBLIC SYNONYM catalogo_general FOR arepazo_prod.tbl_catalogo_platos_interna;

-- Eliminar un sinónimo
DROP SYNONYM IF EXISTS menu_platos;
DROP PUBLIC SYNONYM IF EXISTS catalogo_general;

-- Consultar sinónimos en el catálogo del sistema
SELECT * FROM information_schema.SYNONYMS;

9. Requisitos de Seguridad, Bastionado y Auditoría (mariadb-secure-installation)

El Criterio 3.h exige garantizar el cumplimiento estricto de las directivas de seguridad en el sistema gestor.

El Comando de Bastionado: mariadb-secure-installation

Tras instalar MariaDB, es un requisito de seguridad indispensable ejecutar el asistente interactivo mariadb-secure-installation (o mysql_secure_installation), el cual realiza 4 acciones cruciales:

  1. Establecer contraseña robusta para root: Evitar accesos desprotegidos a la cuenta de superadministrador.
  2. Eliminar usuarios anónimos: Borrar las cuentas con User = '' en mysql.user, que permiten a cualquier usuario no autenticado conectarse sin aportar credenciales.
  3. Desactivar el login remoto de root: Forzar a que root solo pueda autenticarse desde localhost, mitigando ataques de fuerza bruta remotos desde la red.
  4. Eliminar la base de datos 'test': Borrar la base de datos de pruebas inicial y sus privilegios abiertos asociados, evitando que sea utilizada como vector de ataque.

Directivas de Red y Configuración (my.cnf)

# En el archivo de configuración /etc/mysql/my.cnf o /etc/my.cnf.d/server.cnf:
[mysqld]
# Escuchar solo en la interfaz local (si la BD y la app están en el mismo servidor)
bind-address = 127.0.0.1

# O escuchar en la IP privada corporativa:
# bind-address = 192.168.1.10

Auditoría de Cuentas y Privilegios en el Servidor

Un administrador de seguridad debe ejecutar consultas periódicas de auditoría sobre las tablas maestras:

-- 1. Detectar cuentas que tienen el peligroso privilegio GRANT OPTION a nivel global
SELECT User, Host FROM mysql.user WHERE Grant_priv = 'Y';

-- 2. Detectar usuarios con privilegios administrativos de apagado o recarga
SELECT User, Host, Shutdown_priv, Reload_priv, Process_priv, Super_priv, File_priv
FROM mysql.user;

-- 3. Identificar cuentas sin contraseña o con autenticación vulnerable
SELECT User, Host, plugin, password_expired FROM mysql.user;

-- 4. Auditoría de accesos y consultas con MariaDB Audit Plugin
-- Registra en log de texto estructurado quién conectó, cuándo y qué sentencias ejecutó
Resumen de Normas de Seguridad en Producción:
  • Nunca compartir la misma cuenta de usuario entre varios empleados (para no perder la trazabilidad y la responsabilidad individual).
  • Bloquear o eliminar de inmediato (DROP USER o ACCOUNT LOCK) las cuentas de empleados que causen baja en la empresa.
  • Habilitar políticas de contraseñas robustas (plugins simple_password_check o cracklib_password_check).
  • Exigir conexiones seguras y cifradas mediante REQUIRE SSL.
  • Revocar siempre permisos innecesarios de destrucción de tablas (REVOKE DROP) a cuentas operativas.
