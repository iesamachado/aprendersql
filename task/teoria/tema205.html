1. Factores que Afectan al Rendimiento

El rendimiento de una base de datos depende principalmente de dos grandes factores:

  • Consultas bien escritas y optimizadas: La forma en que pedimos los datos impacta enormemente en el tiempo de respuesta.
  • Técnicas de mejora (Índices): Estructuras adicionales que permiten al motor de base de datos encontrar la información rápidamente sin recorrer toda la tabla.

2. Qué NO hacer en una consulta (Buenas Prácticas)

Evitar el SELECT *

Si solo necesitamos los emails de los clientes, no debemos traer toda la tabla. Traer solo las columnas necesarias ahorra memoria y tiempo de procesamiento (y ancho de banda de red).

Filtrar al máximo con el WHERE

Todo lo que podamos filtrar desde el servidor SQL, mejor. Extraer millones de registros para luego filtrarlos en Excel o en la aplicación es ineficiente y consume red y memoria.

Ordenar condiciones en el WHERE

Si usamos un OR, poner primero la condición que se evalúa más rápido y que suele dar verdadero. Así, la base de datos se ahorra procesar condiciones complejas.

Evitar Tablas Temporales

Las tablas temporales no tienen índices, lo que ralentiza las búsquedas. Siempre que sea posible, es mejor utilizar Vistas (Views) en su lugar.

Pon siempre Primary Keys (PK)

Las Claves Primarias son una forma automática y eficiente de indexar las tablas. Toda tabla debería tener una PK.

No usar Cursores en la BBDD

Para recorrer tablas registro a registro, es mucho mejor hacerlo desde la aplicación cliente. Los cursores en el servidor están mal optimizados.

Revisa bien los JOINS

Los joins mal estructurados causan grandes caídas de rendimiento. Es fundamental asegurarse de tener índices en las columnas que participan en la cláusula ON.

3. Índices (Clustered vs Non-Clustered)

Los índices son estructuras de datos que mejoran la velocidad de las operaciones, permitiendo búsquedas y ordenamientos rápidos a costa de algo de espacio en disco y tiempo en las inserciones/modificaciones.

Clustered Index (Agrupados)

  • La tabla se reordena físicamente basándose en el índice.
  • Solo puede haber UNO por tabla (generalmente es la Primary Key).
  • Funciona igual que un diccionario físico o un listín telefónico, donde la información ya está ordenada.

Non-Clustered Index (No Agrupados)

  • No reordena físicamente la tabla. En su lugar, crea una copia indexada de la columna con punteros a la fila real.
  • Podemos crear múltiples índices no agrupados por tabla.
  • Funciona como el índice analítico al final de un libro.
  • En MariaDB (InnoDB), los índices que creamos manualmente son de este tipo.
¡Cuidado: No abusar de los índices!

Los índices ralentizan enormemente la inserción (INSERT), modificación (UPDATE) y borrado (DELETE) de datos, ya que el motor debe actualizar el índice cada vez que los datos cambian. Además, ocupan espacio adicional en disco.

Gestión de Índices en SQL

-- Crear un índice (Non-Clustered en MariaDB)
CREATE INDEX nombre_indice ON tabla(columna1, columna2);

-- Ver los índices de una tabla
SHOW INDEX FROM nombre_tabla;

-- Borrar un índice
DROP INDEX nombre_indice ON tabla;

4. El Comando EXPLAIN en MariaDB

El comando EXPLAIN es fundamental para la monitorización y optimización de consultas. Nos permite ver el plan de ejecución que MariaDB utilizará para resolver nuestra consulta, mostrando si está utilizando índices o haciendo escaneos completos de tabla.

EXPLAIN SELECT * FROM clientes c JOIN pedidos p ON c.id = p.cliente_id WHERE c.pais = 'España';

Al ejecutar EXPLAIN (o EXPLAIN ANALYZE para estadísticas en tiempo real), MariaDB devuelve una tabla con información vital:

Columna Significado e Interpretación
type El tipo de JOIN o escaneo. Es crucial para el rendimiento. Valores de mejor a peor: system, const, eq_ref, ref, range, index, ALL (Significa Table Scan completo, ¡muy lento!).
possible_keys Los índices que MariaDB consideró utilizar para la consulta.
key El índice que MariaDB realmente decidió usar. Si es NULL, no usó ninguno.
rows El número de filas estimadas que el motor debe leer para ejecutar la consulta. A menor número, mejor rendimiento.
Extra Información adicional, como Using index (se resolvió solo con el índice), o Using filesort / Using temporary (generalmente indica problemas de rendimiento a optimizar).

5. Monitorización y Optimización (Binary Logs)

Los Binary Logs (binlog) de MariaDB registran todas las operaciones (cambios) realizadas en la base de datos. Son fundamentales para la replicación y para reconstruir la BBDD desde un backup en caso de desastre.

El problema del espacio y el CAOS

Una mala configuración del binary log puede hacer que nuestro disco se llene rápidamente. Por ejemplo, si configuramos expire-logs-days=0, los logs nunca se borrarán y crecerán hasta el infinito, incluso si borramos los datos originales de las tablas.

¿Cómo verificar el estado de los Binary Logs?
SHOW VARIABLES LIKE 'log_bin';
SHOW VARIABLES LIKE 'expire_logs_days';
SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';
Gestión Correcta de Logs (Purgado)

¡NUNCA BORRAR FICHEROS BINARIOS DIRECTAMENTE DESDE EL SISTEMA OPERATIVO (WINDOWS/LINUX)!

Para liberar espacio de forma segura, se deben usar comandos SQL:

-- Ver los ficheros binarios actuales
SHOW BINARY LOGS;

-- Borrar ficheros hasta una fecha determinada (hasta hoy)
PURGE BINARY LOGS BEFORE NOW();

-- Borrar ficheros hasta un nombre de log específico
PURGE BINARY LOGS TO 'mysql-bin.000006';

-- Rotar el log (cierra el actual y crea uno nuevo)
FLUSH LOGS;
