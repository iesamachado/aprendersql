1. Bases de Datos Distribuidas vs Replicadas

Al escalar aplicaciones o buscar mayor tolerancia a fallos, necesitamos ir más allá de un único servidor. Hay dos estrategias fundamentales con objetivos distintos:

Bases de Datos Distribuidas

Los datos se dividen y almacenan en distintos nodos, pero conforman una única base de datos lógica. Los usuarios acceden sin saber dónde están físicamente los datos (principio de transparencia).

  • Los datos no se duplican: se reparten.
  • Ideal para segmentar información por territorios o delegaciones.
  • Requiere diseño cuidadoso para evitar latencias en consultas cruzadas.
Bases de Datos Replicadas

Existen copias parciales o totales de la misma base de datos en distintos servidores. Los datos se duplican para conseguir disponibilidad y rendimiento.

  • Maestro-Esclavo: escrituras en el Maestro, replicadas a los Esclavos.
  • Multi-Maestro: todos los nodos admiten escrituras y se sincronizan.
  • Aumenta disponibilidad y permite balancear las lecturas.
¿Cuándo usar cada una? La distribución reduce el volumen de datos por nodo (mejor para datos masivos). La replicación aumenta la disponibilidad y reparte la carga de lectura (mejor para aplicaciones con muchas consultas simultáneas). En producción, muchos sistemas combinan ambas estrategias.

2. Fragmentación y Técnicas de Distribución

Para distribuir una base de datos, las tablas se dividen en fragmentos lógicos que se asignan a distintos nodos. Hay tres tipos principales:

Se divide la tabla por filas. Cada nodo tiene un subconjunto de registros con el mismo esquema completo.

  • Por rango: id_cliente BETWEEN 1 AND 10000 → Nodo A. id_cliente > 10000 → Nodo B.
  • Por hash: id_cliente % 2 = 0 → Nodo A. Reparte uniformemente pero dificulta consultas por rango.
  • Por lista: clientes de Madrid → Nodo A. Clientes de Barcelona → Nodo B.
El principal problema del sharding es que los JOIN entre fragmentos de distintos nodos son extremadamente costosos.

Se divide la tabla por columnas. Requiere que la clave primaria esté presente en todos los fragmentos para reconstruir el registro.

Ejemplo: en un servidor guardamos id, nombre, email. En otro, por razones de seguridad, guardamos id, numero_tarjeta, cvv. Permite asegurar columnas sensibles en nodos con más restricciones de acceso.

Combina ambas estrategias. Por ejemplo: primero fragmentación horizontal por país (España → Nodo A, México → Nodo B) y luego cada fragmento se fragmenta verticalmente por tipo de dato (datos públicos / datos sensibles).

Es la más flexible pero también la más compleja de mantener y consultar.

Estrategia¿Cómo funciona?VentajaInconveniente

3. El Motor FEDERATED: Distribución Transparente

El motor FEDERATED de MariaDB permite crear en un servidor una tabla que parece local pero cuyos datos residen en un servidor remoto. Las consultas SQL se redirigen de forma transparente al nodo que tiene los datos reales.

Nodo B (local)
Tiene una tabla FEDERATED. Para el programador, es una tabla normal.
SELECT / INSERT
viajan por la red
Nodo A (remoto)
Tiene la tabla real con los datos. Los almacena en su disco.

La cadena de conexión

Al crear una tabla FEDERATED se le pasa una cadena que define dónde está la tabla real:

CREATE TABLE empleados_remotos (
    id INT AUTO_INCREMENT PRIMARY KEY,
    nombre VARCHAR(100),
    departamento VARCHAR(50)
)
ENGINE = FEDERATED
CONNECTION = 'mysql://usuario:password@192.168.1.100:3306/empresa/empleados';
--                    ^^^^^^^^^^^^^^^  ^^^^^^^^^^^^^^^  ^^^^^^^  ^^^^^^^^
--                    Credenciales     IP:Puerto         BD       Tabla

Limitaciones importantes

El motor FEDERATED tiene restricciones que un administrador debe conocer:
  • No soporta transacciones distribuidas entre los dos nodos.
  • No soporta claves foráneas que apunten a la tabla remota.
  • Sin caché local: cada consulta viaja por la red. La latencia de red afecta directamente al rendimiento.
  • Desactivado por defecto en la mayoría de distribuciones. Hay que habilitarlo en el my.cnf añadiendo la línea federated bajo [mysqld].

Casos de uso reales

  • Acceder a datos de otra sede sin moverlos (consultar datos de la sede de Madrid desde la central en Barcelona).
  • Migraciones graduales: mientras migras datos, mantienes acceso al servidor antiguo vía FEDERATED.
  • Consolidar informes: lanzar SELECT a varias BDs remotas desde un servidor central de análisis.

4. Replicación: Tipos y Topologías

La replicación mantiene copias sincronizadas de una base de datos en múltiples servidores. A diferencia del motor FEDERATED (acceso en tiempo real al remoto), la replicación mantiene una copia local de los datos que se actualiza de forma asíncrona.

¿Cómo funciona internamente?

MariaDB usa el Binary Log (binlog) como mecanismo. Cada cambio en el Maestro se registra en el binlog. El Esclavo lee ese log y aplica los mismos cambios en su copia local.

Master:
  [App] ──► [MariaDB] ──► [mysql-bin.000001]  (Binary Log)
                                    │
                          I/O Thread del Esclavo lee el log por red
Slave:                              │
  [App lectura] ──► [MariaDB copia] ◄── [Relay Log] ◄── Red
                          │
               SQL Thread aplica los cambios del Relay Log

Topologías de Replicación

Un solo Maestro recibe todas las escrituras. Uno o varios Esclavos sirven las lecturas. La replicación fluye en un solo sentido.

Ideal para: aplicaciones con alta carga de lectura (blogs, catálogos, reportes).

Riesgo: si el Maestro cae, no hay nodo que asuma escrituras automáticamente (se necesita failover manual).

El Nodo A es Maestro del Nodo B, y el Nodo B es a su vez Maestro del Nodo C. Los cambios se propagan en cascada. Para ello, B debe tener log_slave_updates = ON en su my.cnf.

A (Master) ──▶ B (Slave de A + Master de C) ──▶ C (Slave de B)

Ventaja: el Maestro original solo sirve a un Esclavo, reduciendo su carga. Ideal para replicar datos entre sedes geográficamente distantes.

Inconveniente: si B cae, C deja de recibir actualizaciones aunque A siga funcionando.

Todos los nodos pueden recibir escrituras y se replican entre sí en ambas direcciones. Ofrece la máxima disponibilidad pero introduce conflictos de escritura: si dos nodos modifican el mismo registro a la vez, hay que resolver cuál prevalece.

Soluciones comunes: Galera Cluster (MariaDB), Group Replication (MySQL). Son más complejos que la replicación estándar pero se usan en producción crítica.

5. Alta Disponibilidad y Tolerancia a Fallos

Tener una réplica no sirve de nada si cuando el Maestro cae nadie sabe qué hacer. La Alta Disponibilidad (HA) es la capacidad del sistema de seguir funcionando cuando un nodo falla.

¿Qué pasa cuando cae un nodo?

EscenarioImpactoSolución
Cae el MaestroLas escrituras dejan de funcionar. Las lecturas en los Esclavos siguen (con datos hasta el momento de la caída).Failover manual: promover uno de los Esclavos a Maestro. Las aplicaciones deben apuntar al nuevo Maestro.
Cae un EsclavoSe pierden capacidades de lectura, pero el sistema sigue operativo.Redistribuir la carga entre los Esclavos restantes. Reconstruir el Esclavo caído cuando vuelva.
Cae un nodo en cadena (B de A→B→C)C deja de actualizarse aunque A siga funcionando.Reconectar C directamente a A, o reconstruir B.

Comandos de diagnóstico esenciales

SHOW MASTER STATUS;
-- Anotar: File y Position (el Esclavo los necesita al configurarse)

SHOW BINARY LOGS;   -- Ver todos los binlogs disponibles

SHOW SLAVE STATUS\G

-- Las líneas más importantes:
-- Slave_IO_Running: Yes      el hilo de red está conectado al Maestro
-- Slave_SQL_Running: Yes     el hilo SQL está aplicando los cambios
-- Seconds_Behind_Master: 0   retraso en segundos (0 = al día)
-- Last_IO_Error:             si hay error de red, aparece aquí
-- Last_SQL_Error:            si hay error al aplicar un cambio, aparece aquí

-- En el Esclavo que vas a promover:
STOP SLAVE;
RESET SLAVE ALL;   -- Desvincularlo del antiguo Maestro

-- Ya actúa como Maestro independiente.
-- Actualizar las aplicaciones para que apunten a esta nueva IP.

-- Si el antiguo Maestro vuelve, lo reconectamos como Esclavo:
CHANGE MASTER TO MASTER_HOST='IP_NUEVO_MASTER', ...;
START SLAVE;
Más allá de la replicación manual: En entornos de producción reales se usan herramientas como MHA, Orchestrator o Galera Cluster que automatizan el failover. La replicación manual que estudias aquí es la base conceptual de todas esas soluciones avanzadas.
