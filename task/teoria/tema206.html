1. Bases de Datos Distribuidas vs Replicadas

Al escalar nuestras aplicaciones o buscar una mayor tolerancia a fallos, necesitamos soluciones que vayan más allá de un único servidor. Aquí surgen dos conceptos clave:

Bases de Datos Distribuidas

Los datos se dividen y almacenan en distintos nodos, pero conforman una única base de datos lógica. Los usuarios o aplicaciones acceden a ella sin necesidad de saber dónde están físicamente los datos (principio de transparencia).

  • Los datos no se duplican (por defecto), se reparten.
  • Ideal para segmentar información por territorios o delegaciones.
  • Requiere un diseño cuidadoso para evitar latencias en consultas cruzadas.
Bases de Datos Replicadas

Existen copias parciales o totales de la misma base de datos en distintos servidores. Todos los nodos (o parte de ellos) contienen la misma información.

  • Distribución Direccional (Maestro-Esclavo): Las modificaciones se hacen en el Maestro y éste las replica a los Esclavos.
  • Descentralizada (Multi-Maestro): Todos los nodos pueden recibir escrituras y se sincronizan entre sí.
  • Aumenta la disponibilidad y permite balancear cargas de lectura.

2. Fragmentación de Datos

Para distribuir una base de datos, solemos emplear la fragmentación, que consiste en dividir las tablas en fragmentos lógicos más pequeños que se reparten entre los nodos.

  • Fragmentación Horizontal

    Se divide la tabla por filas (registros). Por ejemplo, en una tabla Clientes, los clientes de España se almacenan en un servidor en Madrid, y los clientes de México en un servidor en CDMX.

  • Fragmentación Vertical

    Se divide la tabla por columnas. Requiere que la clave primaria esté en todos los fragmentos para poder reconstruir el registro. Ejemplo: en un servidor guardamos el nombre y email, y en otro los datos bancarios por mayor seguridad.

  • Fragmentación Mixta o Híbrida

    Una combinación de ambas estrategias. Primero se fragmenta horizontalmente y luego verticalmente (o viceversa).

Práctica 1: Distribución con MariaDB (Motor FEDERATED)

El motor FEDERATED de MariaDB permite acceder a tablas que residen en bases de datos remotas como si fueran locales. No replica los datos, sino que las consultas se envían al servidor remoto. Esto es ideal para implementar una base de datos distribuida.

Paso 1: Habilitar el motor FEDERATED

En ambos contenedores o servidores MariaDB, asegúrate de tener activado el motor FEDERATED. Edita el archivo de configuración (ej. /etc/mysql/mariadb.conf.d/50-server.cnf) y añade:

[mysqld]
federated

Reinicia el servicio de MariaDB y comprueba que esté activo entrando a MariaDB y ejecutando: SHOW ENGINES;

Paso 2: Crear la tabla real en el Servidor Remoto (Nodo A)

En el servidor donde realmente se guardarán los datos (asumamos que su IP es 192.168.1.100):

CREATE DATABASE empresa;
USE empresa;

CREATE TABLE empleados (
    id INT AUTO_INCREMENT PRIMARY KEY,
    nombre VARCHAR(100),
    departamento VARCHAR(50)
);

INSERT INTO empleados (nombre, departamento) VALUES ('Ana García', 'Ventas');

Paso 3: Crear el usuario para conexión

En el Nodo A, crea un usuario con permisos sobre esa tabla para que el Nodo B pueda conectarse:

CREATE USER 'federado_user'@'%' IDENTIFIED BY 'password123';
GRANT SELECT, INSERT, UPDATE, DELETE ON empresa.empleados TO 'federado_user'@'%';
FLUSH PRIVILEGES;

Paso 4: Crear la tabla FEDERATED en el Servidor Local (Nodo B)

En el servidor local (Nodo B), creamos una tabla con la misma estructura exacta, pero indicando que su motor es FEDERATED y pasándole la cadena de conexión:

CREATE DATABASE empresa_local;
USE empresa_local;

CREATE TABLE empleados_remotos (
    id INT AUTO_INCREMENT PRIMARY KEY,
    nombre VARCHAR(100),
    departamento VARCHAR(50)
)
ENGINE=FEDERATED
CONNECTION='mysql://federado_user:password123@192.168.1.100:3306/empresa/empleados';
¡Listo! Ahora, si haces SELECT * FROM empleados_remotos; en el Nodo B, verás los datos del Nodo A. Cualquier INSERT se guardará remotamente.

Práctica 2: Alta Disponibilidad (Replicación Master-Slave en MariaDB)

Vamos a configurar una topología de Alta Disponibilidad usando Docker Compose. Tendremos un nodo Master (donde se hacen las escrituras) y un nodo Slave (que replica los datos del Master y sirve para lecturas).

Paso 1: Archivo docker-compose.yml

Crea un directorio para tu proyecto y dentro genera el archivo docker-compose.yml:

version: '3.8'
services:
  mariadb-master:
    image: mariadb:10.11
    container_name: mariadb-master
    environment:
      MYSQL_ROOT_PASSWORD: rootpwd
      MYSQL_DATABASE: agenda
    command: [
      "mysqld",
      "--server-id=1",
      "--log-bin=mysql-bin",
      "--bind-address=0.0.0.0"
    ]
    ports:
      - "3306:3306"

  mariadb-slave:
    image: mariadb:10.11
    container_name: mariadb-slave
    environment:
      MYSQL_ROOT_PASSWORD: rootpwd
    command: [
      "mysqld",
      "--server-id=2",
      "--bind-address=0.0.0.0"
    ]
    ports:
      - "3307:3306"
    depends_on:
      - mariadb-master

Levanta los contenedores con: docker-compose up -d

Paso 2: Configurar el Master

Entra al contenedor del Master: docker exec -it mariadb-master mysql -u root -p (contraseña: rootpwd)

Crea un usuario específico para que el Slave pueda conectarse a replicar:

CREATE USER 'replica_user'@'%' IDENTIFIED BY 'replica_pass';
GRANT REPLICATION SLAVE ON *.* TO 'replica_user'@'%';
FLUSH PRIVILEGES;

Revisa el estado del Master y anota el File y Position:

SHOW MASTER STATUS;

(Supongamos que devuelve File: mysql-bin.000001 y Position: 328)

Paso 3: Configurar el Slave e iniciar la replicación

Entra al contenedor del Slave: docker exec -it mariadb-slave mysql -u root -p

Configura la conexión hacia el Master usando los datos anotados (el host es el nombre del servicio en docker-compose):

CHANGE MASTER TO 
    MASTER_HOST='mariadb-master',
    MASTER_USER='replica_user',
    MASTER_PASSWORD='replica_pass',
    MASTER_LOG_FILE='mysql-bin.000001',
    MASTER_LOG_POS=328;

START SLAVE;

Paso 4: Verificar la Replicación

En el Slave, comprueba que la replicación funciona:

SHOW SLAVE STATUS\G

Debes buscar que estas dos variables digan Yes:

  • Slave_IO_Running: Yes
  • Slave_SQL_Running: Yes
¡Comprobación final! Entra al Master, crea una tabla e inserta un dato en la BBDD agenda. Luego entra al Slave y haz un SELECT. ¡El dato estará ahí automáticamente!
