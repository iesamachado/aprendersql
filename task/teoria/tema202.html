1. Condiciones de Inicio, Parada y Modo Rescate del Servicio (Criterio 2a)

En servidores Linux modernos (Ubuntu, Debian, RedHat, Rocky), el servicio del gestor MariaDB se administra mediante systemd a través del comando systemctl.

Comandos de Servicio (systemctl)
# Iniciar el servicio MariaDB
sudo systemctl start mariadb

# Detener el servicio de forma limpia
sudo systemctl stop mariadb

# Reiniciar el servicio (aplica cambios de my.cnf)
sudo systemctl restart mariadb

# Comprobar estado operativo y últimos logs
sudo systemctl status mariadb

# Habilitar inicio automático en el arranque del SO
sudo systemctl enable mariadb

# Deshabilitar el arranque automático
sudo systemctl disable mariadb
Herramientas de Consola y Parada Segura

Además de systemctl, existen comandos nativos del propio gestor:

  • mysqladmin -u root -p shutdown: Ordena al gestor vaciar buffers a disco (flush) y realizar una parada limpia y controlada sin dañar tablas InnoDB.
  • mariadbd-safe (o mysqld_safe): Script wrapper que monitoriza el demonio mariadbd y lo reinicia automáticamente en caso de fallo o caída imprevista.
  • Señales del SO: El comando systemctl stop envía una señal SIGTERM (15) para permitir una parada limpia; NUNCA debe usarse SIGKILL (9) ya que aborta el proceso de forma abrupta arriesgando la corrupción de datos.
  • PID del proceso: El archivo configurado en pid-file = /var/run/mysqld/mysqld.pid almacena el Process ID (PID) del demonio en ejecución.
Modo Rescate: Recuperación ante Desastres y Contraseñas de Root

Si el administrador pierde la contraseña de root o una directiva corrupta impide validar permisos, se puede arrancar el demonio omitiendo la comprobación de tablas de privilegios: 

# 1. Detener el servicio habitual
sudo systemctl stop mariadb

# 2. Iniciar el motor en modo rescate sin red para evitar intrusiones
sudo mysqld_safe --skip-grant-tables --skip-networking &

# 3. Conectarse a la consola sin contraseña
mariadb -u root

# 4. En la consola MariaDB, recargar permisos y cambiar la clave
FLUSH PRIVILEGES;
ALTER USER 'root'@'localhost' IDENTIFIED BY 'NuevaContraseñaSegura2024!';
FLUSH PRIVILEGES;
exit;

# 5. Detener el proceso de rescate y arrancar normalmente con systemd
sudo killall mysqld_safe mariadbd
sudo systemctl start mariadb

2. Selección de Motores de Almacenamiento: InnoDB vs MyISAM vs MEMORY (Criterio 2b)

La arquitectura modular de MariaDB permite asignar diferentes motores de almacenamiento (Storage Engines) a cada tabla según los requisitos de explotación y concurrencia.

Motor Transacciones (ACID) Nivel de Bloqueo Claves Foráneas (FK) Caso de Uso Recomendado
InnoDB (Default) Sí (ACID) Fila (Row-level) Sí Aplicaciones transaccionales (OLTP), comercio electrónico, donde la integridad, el soporte de COMMIT / ROLLBACK y la concurrencia masiva de escritura son críticas.
MyISAM No Tabla (Table-level) No Tablas de solo lectura, catálogos estáticos o históricos antiguos con consultas masivas de lectura y cero transacciones.
MEMORY (HEAP) No Tabla No Tablas temporales en RAM, sesiones o tablas de búsqueda rápida (lookups). Atención: Sus datos desaparecen si se reinicia el servidor.
CSV No Tabla No Almacena registros en ficheros de texto plano CSV. Ideal para exportar/importar datos fácilmente con hojas de cálculo.
ARCHIVE No Fila No Logs y auditorías históricas enormes: solo permite INSERT y SELECT con alta compresión gzip integrada (no admite UPDATE ni DELETE).

Gestión de Motores en SQL y my.cnf

-- Ver todos los motores soportados (el predeterminado muestra 'DEFAULT' en la columna Support)
SHOW ENGINES;

-- Crear una tabla especificando un motor concreto
CREATE TABLE pedidos (
    id INT AUTO_INCREMENT PRIMARY KEY,
    total DECIMAL(10,2)
) ENGINE = InnoDB;

-- Cambiar el motor de una tabla existente (convierte datos internamente)
ALTER TABLE logs_antiguos ENGINE = ARCHIVE;

-- Configurar el motor por defecto en /etc/mysql/my.cnf bajo [mysqld]
# default_storage_engine = InnoDB
Estructura de ficheros en disco: En MyISAM cada tabla se guardaba en tres ficheros (.frm formato, .MYD datos, .MYI índices). En InnoDB moderno, la estructura y datos se almacenan en ficheros tablespace .ibd por tabla (cuando innodb_file_per_table = 1) y en los archivos del sistema ibdata1 y redo logs (ib_logfile0).

3. Aseguramiento de Cuentas de Administración y Recuperación de Root (Criterio 2c)

La cuenta de superadministrador root posee control absoluto sobre el motor de base de datos. Asegurarla es la primera intervención de seguridad obligatoria tras la instalación.

mariadb-secure-installation (o mysql_secure_installation)

Este asistente de bastionado interactivo (invocado indistintamente como mariadb-secure-installation o mysql_secure_installation) realiza 4 acciones vitales:

  1. Establecer una contraseña robusta para root.
  2. Eliminar usuarios anónimos (cuentas con User = '').
  3. Desactivar el acceso remoto de root (forzar 'root'@'localhost').
  4. Eliminar la base de datos de pruebas test y sus permisos abiertos.
Autenticación por Socket UNIX (unix_socket)

Por defecto en instalaciones de MariaDB en Linux, la cuenta root utiliza el plugin unix_socket. Esto permite que el usuario root del sistema operativo pueda conectarse sin contraseña con sudo mariadb, pero impide completamente que nadie acceda a root mediante contraseña remota desde la red.

Buenas Prácticas de Cuentas Administrativas

-- 1. Crear un administrador delegado para tareas cotidianas y no usar root
CREATE USER 'admin_secundario'@'192.168.1.%' IDENTIFIED BY 'AdminFuerte$2024' REQUIRE SSL;
GRANT ALL PRIVILEGES ON *.* TO 'admin_secundario'@'192.168.1.%' WITH GRANT OPTION;

-- 2. Asegurar que root NO pueda conectar desde cualquier host (%)
DROP USER IF EXISTS 'root'@'%';
DELETE FROM mysql.user WHERE User = 'root' AND Host NOT IN ('localhost', '127.0.0.1', '::1');
FLUSH PRIVILEGES;

-- 3. Forzar cambio de clave y bloqueo preventivo
ALTER USER 'admin_secundario'@'192.168.1.%' PASSWORD EXPIRE;
ALTER USER 'admin_secundario'@'192.168.1.%' ACCOUNT LOCK;
ALTER USER 'admin_secundario'@'192.168.1.%' ACCOUNT UNLOCK;

-- 4. Cuenta para copias lógicas con mariadb-dump (mínimo privilegio: lectura y bloqueo, sin ALL PRIVILEGES)
GRANT SELECT, SHOW VIEW, TRIGGER, LOCK TABLES ON *.* TO 'backup_user'@'localhost';

4. Configuración de Herramientas y Software Cliente (Criterio 2d)

El acceso a MariaDB se realiza mediante clientes de consola (CLI) o entornos de desarrollo gráficos (GUI) a través de los puertos de red del gestor.

Herramientas Gráficas (DBeaver, Workbench)
  • DBeaver: Cliente universal multiplataforma basado en drivers JDBC. Permite autocompletado, modelado ER y visualización de datos.
  • Túnel SSH: Para conectar DBeaver a un servidor MariaDB remoto protegido sin exponer el puerto 3306 a internet, se configura una conexión con túnel SSH intermedio.
  • phpMyAdmin: Interfaz web clásica desarrollada en PHP para administración en servidores web compartidos.
Archivo de Opciones del Cliente (~/.my.cnf)

Para automatizar scripts y conectar por consola sin teclear contraseñas ni exponerlas en el historial de comandos, se configura el fichero ~/.my.cnf en el directorio home del usuario: 

# ~/.my.cnf (Debe tener permisos chmod 600)
[client]
user = admin_secundario
password = MiContraseñaSecreta
host = localhost
port = 3306

Es obligatorio proteger el archivo con chmod 600 ~/.my.cnf para que otros usuarios del sistema no puedan leer las credenciales.

5. Conectividad en Red y Cortafuegos: bind-address, Puertos y TLS (Criterio 2e)

La configuración de red en el archivo my.cnf define qué interfaces y máquinas remotas pueden comunicarse con el motor de base de datos.

Directiva Valores Típicos Comportamiento y Seguridad
bind-address 127.0.0.1 Solo acepta conexiones locales (loopback). Inaccesible desde cualquier otra máquina de la red. Máxima seguridad.
bind-address 0.0.0.0 (o ::) Escucha en todas las tarjetas de red e interfaces del servidor. Necesario para permitir accesos remotos.
bind-address 192.168.1.50 Escucha exclusivamente en la tarjeta de red asociada a esa IP privada (ej. red interna de servidores).
port 3306 (predeterminado) Puerto TCP estándar asignado por la IANA a MySQL/MariaDB. Puede cambiarse para reducir escaneos automatizados de bots.
skip-networking (activado / sin valor) Desactiva completamente la pila TCP/IP. El motor solo acepta conexiones locales mediante socket UNIX (/var/run/mysqld/mysqld.sock).
skip-name-resolve (activado / sin valor) Desactiva la resolución inversa de DNS en cada conexión entrante, acelerando drásticamente el establecimiento de sesiones remotas. Precaución crítica: las cuentas de usuario deben crearse siempre con direcciones IP numéricas (ej. 'user'@'192.168.1.%') y nunca con nombres de host o dominios FQDN.

Reglas de Cortafuegos en el Sistema Operativo (UFW / iptables)

# En Ubuntu/Debian con UFW:
# Permitir conexiones al puerto 3306 únicamente desde la subred del servidor web
sudo ufw allow from 192.168.1.0/24 to any port 3306 proto tcp

# Comprobar qué puertos están escuchando en el servidor
sudo ss -tulpn | grep 3306
# o con netstat:
sudo netstat -tlpn | grep mariadbd

6. Características por Defecto: Charset (utf8mb4), Collation y sql_mode (Criterio 2f)

El juego de caracteres, la colación y el modo SQL determinan cómo se almacena, compara e interpreta el texto y las reglas de validación en las tablas creadas por defecto.

utf8mb4 (Estándar Actual)

En MariaDB/MySQL, el charset clásico utf8 era en realidad utf8mb3 (máximo 3 bytes por carácter). El estándar moderno obligatorio es utf8mb4, que soporta 4 bytes por carácter, permitiendo almacenar el conjunto Unicode completo, caracteres asiáticos y emojis sin pérdidas.

Collation (_ci vs _cs vs _bin)
  • _ci (Case Insensitive): No distingue entre mayúsculas y minúsculas ('Madrid' = 'madrid'). Es la más común (ej. utf8mb4_unicode_ci o utf8mb4_general_ci).
  • _cs (Case Sensitive): Distingue mayúsculas y minúsculas.
  • _bin (Binary): Comparación binaria exacta por valor de código byte.
sql_mode Estricto

STRICT_TRANS_TABLES y NO_ENGINE_SUBSTITUTION garantizan que si un usuario intenta insertar un valor inválido (ej. texto en un entero o fecha incorrecta), el motor lance un error fatal en lugar de insertar ceros o truncar en silencio. El modo ERROR_FOR_DIVISION_BY_ZERO evita que devuelva NULL sin aviso, y ANSI_QUOTES trata las comillas dobles como identificadores.

Gestión de Charset, Collation y Modos en SQL

-- 1. Crear una base de datos especificando charset y collation
CREATE DATABASE arepazo CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- 2. Consultar colaciones disponibles para utf8mb4
SHOW COLLATION WHERE Charset = 'utf8mb4';

-- 3. Convertir una tabla existente completa a utf8mb4
ALTER TABLE platos CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- 4. Consultar el sql_mode activo en sesión y global
SELECT @@SESSION.sql_mode;
SELECT @@GLOBAL.sql_mode;

# En /etc/mysql/my.cnf bajo [mysqld]:
[mysqld]
character-set-server = utf8mb4
collation-server     = utf8mb4_unicode_ci
sql_mode             = STRICT_TRANS_TABLES,ERROR_FOR_DIVISION_BY_ZERO,NO_AUTO_CREATE_USER,NO_ENGINE_SUBSTITUTION,ANSI_QUOTES

7. Parámetros de Conexión, Timeouts y Memoria (Criterio 2g)

Dimensionar correctamente el número de conexiones permitidas y los buffers de memoria es imprescindible para evitar caídas por saturación de RAM o el error "Too many connections".

Parámetro Descripción Valor Típico / Recomendado
max_connections Número máximo de conexiones de clientes simultáneas. Cada conexión consume memoria adicional (hilos, buffers). 150 (default) a 500+ según RAM.
max_user_connections Número máximo de conexiones simultáneas permitidas a una misma cuenta de usuario individual (evita monopolios). 0 (ilimitado) o 20-50 en hosting.
wait_timeout Segundos que el servidor espera en una conexión no interactiva inactiva (ej. pool de apps web) antes de cerrarla. 600 (10 min) o 300 en web (default: 28800s = 8h).
interactive_timeout Segundos de espera en conexiones interactivas (consolas CLI, DBeaver) antes de cerrarlas por inactividad. 3600 (1 hora) a 28800 (8 horas).
connect_timeout Segundos que el servidor espera el paquete de saludo (handshake) antes de abortar la conexión con "Bad handshake". 10 segundos.
innodb_buffer_pool_size El parámetro de rendimiento más importante: la caché en memoria RAM donde InnoDB guarda datos e índices. 50% al 70-80% de la memoria RAM total en servidores dedicados.

Inspección en Tiempo Real y Cambios Dinámicos (SET GLOBAL)

-- Comprobar el valor configurado de las variables
SHOW VARIABLES LIKE 'max_connections';
SHOW VARIABLES LIKE '%timeout%';
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';

-- Comprobar el estado real de conexiones en vivo
SHOW STATUS LIKE 'Threads_connected';     -- Conexiones abiertas en este instante
SHOW STATUS LIKE 'Max_used_connections';  -- Pico máximo de conexiones alcanzado desde el arranque

-- Modificar parámetros dinámicos en caliente (sin reiniciar el servidor)
SET GLOBAL max_connections = 250;
SET GLOBAL wait_timeout = 600;

-- Consultar procesos en ejecución y terminar conexiones bloqueadas si es necesario
SHOW PROCESSLIST;
KILL 42; -- Termina el hilo de conexión con ID 42

-- ⚠️ Recordatorio: Los cambios con SET GLOBAL se pierden si el servidor se reinicia;
-- para hacerlos permanentes deben escribirse en el archivo my.cnf.

8. Registro y Diagnóstico: Error Log, General Log y Slow Query Log

MariaDB genera diferentes tipos de archivos de registro que son cruciales para el monitoreo, la auditoría y la detección de cuellos de botella.

Error Log

Registra incidencias de inicio, parada y errores críticos del servidor. Es el primer archivo que debe inspeccionarse si MariaDB no arranca.

log_error = /var/log/mysql/error.log

General Query Log

Registra absolutamente todas las sentencias SQL recibidas de cualquier cliente y las conexiones. Muy útil en depuración puntual, pero degrada el rendimiento y consume gigabytes de disco rápidamente.

general_log = 0 (desactivado en prod)

Slow Query Log

Registra consultas que tardan más del umbral long_query_time (ej. 2 segundos) o que no usan índices (log_queries_not_using_indexes = 1). Fundamental para optimización.

slow_query_log = 1

9. Documentación y Control de Cambios de Configuración (Criterio 2h)

En infraestructuras profesionales, cualquier intervención sobre el archivo my.cnf es un cambio de producción crítico que debe quedar documentado de forma auditable.

Requisitos de Documentación de Cambios
  • Parámetro modificado: Nombre exacto del parámetro y valor anterior vs valor nuevo.
  • Motivo técnico o métrica justificativa: Por qué se realizó el cambio (ej. "el slow query log registraba 350 consultas lentas/hora y el ratio de cache hit era de solo el 70%").
  • Fecha, hora y responsable: Identificación del administrador que ejecutó el cambio.
  • Métrica de impacto verificada: Comprobación posterior de si la intervención resolvió el problema (ej. "el cache hit subió al 95%").
  • Plan de reversión (Rollback): Procedimiento exacto para deshacer el cambio si surgen efectos secundarios.
Ejemplo de Registro en CHANGELOG.md
## [2025-04-10] — bernat@db-server-01

**Cambio:** `innodb_buffer_pool_size`: 256M → 1G, `max_connections`: 150 → 300
**Motivo:** Errores "Too many connections" detectados en horas pico (13:00 - 15:00) en el restaurante El Arepazo.
**Impacto:** Cero errores de conexión tras 48h de monitorización con SHOW STATUS LIKE 'Max_used_connections'.
**Reversión:** Modificar my.cnf a 256M y 150 conexiones, y reiniciar mariadb.
Control de Versiones e IaC: Versionar /etc/mysql/ con Git y herramientas de automatización (Ansible) permite desplegar configuraciones idénticas y auditar cada cambio con git diff.
Cumplimiento (ENS / ISO 27001) y Reducción del MTTR: Una documentación auditable es exigida por normativas como el Esquema Nacional de Seguridad (ENS) e ISO 27001, y reduce drásticamente el Tiempo Medio de Recuperación (MTTR) ante caídas del servicio.
