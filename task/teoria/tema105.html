Tema 5.1: Modificando datos, DML

¡Cuidado!

Vamos a modificar datos. Tendremos que tener mucho cuidado. Nos debe "temblar" el dedo antes de darle a ejecutar. No siempre tendremos un backup para volver al punto anterior.

Guardar la partida: Utiliza BEGIN (Instrucción SQL para modificar/borrar/insertar datos) y ROLLBACK. Si lanzamos estas líneas juntas, NO MODIFICAMOS la BBDD, pero sí vemos las líneas afectadas. ¡PROBAD SIEMPRE VUESTROS DELETES/UPDATES!

3.1 INSERT (Crear)

El comando INSERT permite añadir datos. Hay 3 formas principales de usarlo:

  • Con valores puestos a "pelo" (muy útil si queremos insertar una fila, o insertar fila a fila).
  • Insertando datos de otra consulta (insertará tantas filas como resultados de la consulta, muy útil masivamente).
  • Insertando desde un CSV.
¿Y los ids autoincrements?
Si nuestra tabla tiene un campo autoincremental (normalmente el id) NO DEBEREMOS AÑADIRLO. Nos "saltamos" ese campo.
Con Identity: INSERT INTO personas (apellido,nombre,direccion) VALUES('costa','Miquel','calle')
Sin Identity: INSERT INTO personas (personaid,apellido,nombre,direccion) VALUES('2','costa','Miquel','calle')
1. Manual ("A pelo")

Añades valores estáticos que tú escribes.

INSERT INTO Platos (nombre, precio) 
VALUES ('Arepa Nueva', 5.50);
2. Desde una Consulta

Los datos vienen de un SELECT previo.

INSERT INTO Clientes_VIP (nombre) 
SELECT nombre FROM Clientes WHERE puntos > 100;
3. Insertar desde un CSV
BULK INSERT equipos FROM '/var/opt/mssql/backup/futbol/clubs.csv' 
WITH ( FIELDTERMINATOR = ',' , ROWTERMINATOR = '0x0a' )

La ruta después del FROM le indicamos la ruta DENTRO del contenedor o servidor donde va a encontrar el CSV.

3.2 UPDATE (Actualizar)

A diferencia de con el DDL, no modificaremos un campo de int a varchar. Cambiaremos el contenido de una tabla. UPDATE modifica datos ya existentes. Es CRÍTICO usar siempre WHERE, de lo contrario, ¡actualizarás TODAS las filas de la tabla con el mismo valor!

También podemos hacerlo de varias formas: Modificar un dato a pelo o Modificar un dato desde una consulta.

-- SINTAXIS BÁSICA (¡CUIDADO CON EL WHERE!)
UPDATE Tabla SET columna = nuevo_valor WHERE condicion;

3.3 DELETE (Borrar)

El temible DELETE. Sirve para borrar datos. Borramos tantos datos como queramos y le indiquemos en el WHERE. Al igual que con el UPDATE, si olvidas el WHERE, borrarás todo el contenido de la tabla. No se pueden recuperar los datos eliminados sin un backup.

¡JAMÁS ME OLVIDO DE PONER EL WHERE EN EL DELETE FROM!

Si quiero borrar la tabla entera, escribiré: DELETE FROM personas WHERE 1=1. SIEMPRE PONDRÉ EL WHERE.

En el UPDATE también escribiré SIEMPRE el WHERE. AUNQUE SEA 1=1.

-- SINTAXIS BÁSICA
DELETE FROM Tabla WHERE condicion;

3.4 Modificaciones Avanzadas

3.4.1 INSERT desde SELECT

Imagina que quieres regalar un cupón a todos los usuarios que han comprado 'Arepas'. No necesitas un script de Python. ¡Puedes insertar directamente el resultado de una consulta compleja!

Concepto: INSERT INTO ... SELECT ... permite copiar datos de una tabla a otra basándose en una consulta. Es muy potente para migraciones o tablas de resumen.
INSERT INTO Cupones (cliente_id, codigo) 2 Campos = 2 Campos
SELECT DISTINCT c.id, 'AREPA_LOVER'
FROM Clientes c INNER JOIN Pedidos p ON c.id = p.cliente_id WHERE p.producto = 'Arepa'

3.4.2 UPDATE desde SELECT

¿Calcular una columna compleja? Primero visualízala con un SELECT. Luego cambia la coma , por un igual = y el SELECT por UPDATE.

SELECT UPDATE Productos p SET
p.popularidad , = COUNT(d.id)
FROM Productos p INNER JOIN DetallesPedido d ON p.id = d.producto_id
GROUP BY p.id

3.4.3 DELETE con Subconsulta (Comando IN en el where)

Es muy útil en el DELETE el where con un IN y una subconsulta. Podemos localizar todos los Id's con una subconsulta y ponerla en un IN para borrar varios registros automáticamente.

¡IMPORTANTE! La subconsulta dentro del IN (...) debe devolver UNA SOLA COLUMNA (generalmente el ID). Si devuelves `SELECT *`, fallará.

Borrar usuarios que no han hecho pedidos en el último año.

DELETE FROM Usuarios WHERE id IN ( ... );

3.5 Caso Real: Una Tienda

3.5.1 GDPR (Borrado de Clientes)

El Problema: Un cliente pide la baja. ¿Qué haces con sus Pedidos? Tienes 3 estrategias comunes.

Destructivo: Borras al cliente Y TAMBIÉN sus pedidos. Pierdes historial de ventas.
START TRANSACTION;
-- 1. Borrar detalles (Un IN con JOIN dentro)
DELETE FROM DetallesPedido WHERE pedido_id IN (
  SELECT p.id FROM Pedidos p
  INNER JOIN Clientes c ON p.cliente_id = c.id
  WHERE c.email = 'juan@gmail.com'
);
-- 2. Borrar pedidos del cliente
DELETE FROM Pedidos WHERE cliente_id IN (
  SELECT id FROM Clientes WHERE email = 'juan@gmail.com'
);
-- 3. Finalmente, borrar al cliente
DELETE FROM Clientes WHERE email = 'juan@gmail.com';
COMMIT;
Recomendado (GDPR): Mantienes los datos de ventas pero el cliente se vuelve anónimo.
UPDATE Clientes
SET nombre = 'Anónimo',
    email = CONCAT('borrado_', id, '@anonimo.com'),
    telefono = NULL,
    direccion = 'Destruido'
WHERE email = 'juan@gmail.com';
-- Resultado: Los pedidos siguen existiendo, pero son de "Anónimo".
Híbrido: Los pedidos quedan "huérfanos" (sin cliente) y borras la ficha.
START TRANSACTION;
-- 1. Desvincular pedidos (FK debe permitir NULL)
UPDATE Pedidos SET cliente_id = NULL
WHERE cliente_id = (SELECT id FROM Clientes WHERE email = 'juan@gmail.com');
-- 2. Ahora es seguro borrar al cliente
DELETE FROM Clientes WHERE email = 'juan@gmail.com';
COMMIT;

3.6 Seguridad: DELETE sin WHERE

El Peligro es Real

Ejecutar un DELETE o UPDATE sin filtrar afecta a TODAS las filas. Si trabajas en producción, esto es despido inmediato.

3.6.1 Transacciones: El "Ctrl+Z" de la Base de Datos

¿Alguna vez has enviado un mensaje de WhatsApp a la persona equivocada y has deseado borrarlo antes de que lo lea? Bueno, en SQL, SI PUEDES (si eres listo).

Regla de Oro para Sobrevivir

Antes de ejecutar cualquier DELETE o UPDATE masivo, ¡abre una transacción! Es tu red de seguridad. Si metes la pata (y lo harás), puedes hacer ROLLBACK y volver al pasado como si nada hubiera ocurrido.

-- 1. Empieza la magia (Modo Seguro ON)
BEGIN;

-- 2. Ejecuta tu sentencia peligrosa
DELETE FROM Usuarios; -- ¡UPS! ¡OLVIDÉ EL WHERE! 😱

-- 3. ¿El resultado es un desastre?
ROLLBACK; -- ¡Fiú! Todo vuelve a estar bien. 😌

-- 4. ¿Todo correcto? (Solo entonces...)
COMMIT; -- Guardar cambios para siempre.

Tu ángel de la guarda se llama ROLLBACK

Filosofía de Vida (Tatuajes Obligatorios)
NI UN DELETE/UPDATE SIN WHERE
NI UN DELETE/UPDATE SIN BEGIN ROLLBACK
Consejo Pro: Siempre escribe el SELECT antes que el DELETE para verificar qué vas a borrar.
SELECT * FROM Usuarios WHERE id = 5; -> ¿Es el correcto? -> DELETE ...

4. Bloqueos de Registros (Locking) Criterio 5.h BOJA

En un entorno multiusuario varios procesos pueden intentar modificar el mismo registro al mismo tiempo. MariaDB utiliza un sistema de bloqueos para garantizar que las modificaciones sean seguras y coherentes.

Normativa BOJA — Criterio 5.h: «Se han identificado los efectos de las distintas políticas de bloqueo de registros.»
Bloqueo Compartido (Shared Lock / READ)

Varios procesos pueden leer el mismo registro a la vez. Ninguno puede modificarlo mientras el bloqueo compartido está activo.

-- Adquirir bloqueo de lectura sobre una tabla:
LOCK TABLES Pedidos READ;

SELECT * FROM Pedidos WHERE estado = 'Pendiente';

-- Liberar el bloqueo:
UNLOCK TABLES;

✅ Útil para obtener una «foto» consistente sin impedir que otros lean.

Bloqueo Exclusivo (Exclusive Lock / WRITE)

Solo un proceso puede escribir en el recurso bloqueado. Ningún otro puede leer ni escribir hasta que se libere.

LOCK TABLES Pedidos WRITE;

UPDATE Pedidos SET estado = 'Enviado'
WHERE pedido_id = 42;

UNLOCK TABLES;

⚠️ Si no liberas el bloqueo, otros procesos quedarán esperando indefinidamente.

Bloqueo a nivel de fila con SELECT ... FOR UPDATE (InnoDB)

El motor InnoDB soporta bloqueos a nivel de fila, mucho más granulares y eficientes que los bloqueos de tabla:

-- Ejemplo: proceso de compra que bloquea el stock de un producto
BEGIN;

-- Bloquear solo la fila del producto (otros procesos siguen trabajando con el resto):
SELECT stock FROM Platos WHERE plato_id = 7 FOR UPDATE;

-- Si hay stock, decrementar:
UPDATE Platos SET stock = stock - 1 WHERE plato_id = 7;

COMMIT;  -- Libera el bloqueo de fila automáticamente
FOR UPDATE bloquea solo las filas del resultado, no la tabla entera. Es el enfoque correcto en aplicaciones de producción.
Problemas clásicos de concurrencia sin bloqueos
Problema¿Qué ocurre?Ejemplo
Lectura sucia
(Dirty Read)		 Un proceso lee datos que otro ha modificado pero aún no ha hecho COMMIT. Proceso A reduce stock a 0 (sin COMMIT). Proceso B ve stock=0 y rechaza la venta. Proceso A hace ROLLBACK: el stock sigue siendo 1.
Lectura no repetible
(Non-Repeatable Read)		 Un proceso lee el mismo dato dos veces y obtiene valores distintos. Proceso A lee precio=5€. Proceso B cambia precio a 6€ y hace COMMIT. Proceso A vuelve a leer: 6€.
Escritura fantasma
(Phantom Read)		 Una misma consulta devuelve filas distintas en dos ejecuciones dentro de la misma transacción. Proceso A consulta 10 pedidos pendientes. Proceso B inserta 3 más. Proceso A vuelve a consultar: 13.

Ejercicio — Bloqueos

Enunciado: Abre dos pestañas de DBeaver conectadas a la BD del Arepazo. En la pestaña 1, inicia una transacción y bloquea con FOR UPDATE el plato con plato_id = 1. Sin hacer COMMIT, intenta desde la pestaña 2 hacer un UPDATE sobre ese mismo plato. Observa qué ocurre. Luego haz COMMIT en la pestaña 1 y comprueba que la pestaña 2 continúa.

Ver script para pestaña 1 
-- PESTAÑA 1: bloquear y esperar
BEGIN;
SELECT plato_id, nombre, precio FROM Platos WHERE plato_id = 1 FOR UPDATE;
-- NO hagas COMMIT todavía. Ahora ejecuta el script en la pestaña 2.
-- Cuando quieras liberar el bloqueo:
COMMIT;
Ver script para pestaña 2 
-- PESTAÑA 2: intentar modificar el registro bloqueado
BEGIN;
UPDATE Platos SET precio = 9.99 WHERE plato_id = 1;
-- Este UPDATE quedará ESPERANDO hasta que la pestaña 1 haga COMMIT o ROLLBACK
COMMIT;
