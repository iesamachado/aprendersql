1. Sistemas Lógicos de Almacenamiento

Antes de las bases de datos, la información persistente se guardaba exclusivamente mediante el sistema de ficheros del Sistema Operativo.

Según Contenido
  • Texto: Organizado con caracteres legibles (txt, csv).
  • Binario: Datos complejos que requieren decodificación (imágenes, ejecutables).
Según Organización
  • Secuenciales: Para acceder a un dato, hay que leer los anteriores (ej. cintas magnéticas).
  • Relativos/Directos: Acceso mediante una posición calculada (hash).
  • Indexados: Utilizan un índice auxiliar para localizar registros rápidamente.
Problemas de usar solo ficheros clásicos

Redundancia (datos duplicados), inconsistencia (datos que no coinciden en distintos ficheros), dificultad de acceso concurrente, y dependencia estricta entre el programa y la estructura del fichero.

Formatos de Intercambio: XML y JSON

Para solucionar parte de los problemas de los ficheros de texto plano y facilitar la comunicación entre aplicaciones (APIs, servicios web), nacieron formatos estructurados. No sustituyen a una Base de Datos para grandes volúmenes, pero son esenciales hoy en día.

XML (eXtensible Markup Language)

Basado en etiquetas jerárquicas (similar al HTML). Es muy descriptivo pero ocupa más espacio (verboso).

<alumno>
  <id>101</id>
  <nombre>Ana Pérez</nombre>
  <curso>ASIR</curso>
</alumno>
JSON (JavaScript Object Notation)

Basado en pares de "clave-valor". Es más ligero, rápido de procesar y el estándar actual en desarrollo web.

{
  "alumno": {
    "id": 101,
    "nombre": "Ana Pérez",
    "curso": "ASIR"
  }
}

2. Tipos de Bases de Datos según el Modelo de Datos

A lo largo de la historia, las bases de datos han evolucionado para organizar la información de distintas formas lógicas.

Jerárquicas y en Red (Históricas)

Primeros modelos (años 60). Los datos se organizan como un árbol invertido (jerárquico, como carpetas) o como un grafo multidireccional (red, CODASYL). Muy rígidas y complejas de programar.

Relacionales (SQL)

El estándar de la industria (años 70, E.F. Codd). La información se estructura en tablas (relaciones) bidimensionales de filas y columnas. Se enlazan mediante claves primarias y foráneas. Son muy robustas y aseguran la consistencia (ACID).

Orientadas a Objetos

Almacenan objetos completos (estado y comportamiento), similares a la programación orientada a objetos (Java, C++). Evitan la conversión entre tablas y objetos en memoria, aunque su uso es de nicho.

NoSQL (Documentales, Clave-Valor...)

Sistemas modernos para Big Data (MongoDB, Redis, Neo4j). Rompen el esquema de tablas rígidas. Son altamente escalables y flexibles. Complementan a las BD relacionales, no las sustituyen.

3. ¿Qué es una BBDD y un SGBD?

Base de Datos (BD)

Es un conjunto de datos estructurados, relacionados entre sí y almacenados bajo un mismo contexto.

Sistema Gestor (SGBD)

Es el software especializado que ejerce de intermediario absoluto entre los usuarios (o aplicaciones) y esos datos físicos.

Diseccionando la definición
1. Datos

Es la materia prima en bruto. Puede ser texto (un nombre), números (un precio) o fechas. Por sí solos, descontextualizados, no dicen mucho.

2. Estructurados y Relacionados

No están tirados al azar en un texto. Siguen un orden estricto (filas y columnas) y se conectan lógicamente (ej: un "Alumno" se relaciona con sus "Asignaturas").

3. Mismo Contexto

Tienen un propósito y ámbito común. Jamás mezclamos las recetas médicas de un hospital con el inventario de una ferretería en la misma base de datos.

4. SGBD (Intermediario)

Tú nunca tocas los bits de los datos directamente en el disco. Le pides las cosas al SGBD hablando en SQL, y él los busca, ordena y te los entrega de forma segura.

Aclaración vital: Cliente vs Motor vs Datos

Es un error extremadamente común entre principiantes confundir el programa que usamos para ver las tablas (Cliente) con el motor que las gestiona (SGBD) y con los datos en sí.

1. Cliente SQL

Es la herramienta gráfica (o consola) que utilizas tú para escribir las consultas. No guarda ni gestiona los datos, solo se conecta al motor para pedírselos.

Ej: phpMyAdmin, DBeaver.

2. SGBD (Motor)

Es el "cerebro" (servicio en el servidor). Recibe la petición del Cliente, procesa la consulta y decide cómo buscar o guardar la información de forma segura.

Ej: MySQL, PostgreSQL.

3. Base de Datos

Ficheros físicos reales en el disco duro del servidor donde residen los datos puros. Tú nunca los tocas directamente, solo el SGBD tiene permiso.

Ej: Ficheros .ibdata o .frm.

Características y Utilidad de un SGBD:

  • Abstracción e Independencia: El programador no necesita saber cómo se guardan físicamente los bytes en el disco.
  • Integridad: Mecanismos que impiden meter una letra en un campo numérico (reglas, restricciones).
  • Seguridad: Autenticación, roles y permisos de lectura/escritura por tabla.
  • Transacciones (ACID): Operaciones en bloque seguras ("todo o nada").
  • Concurrencia: Controla bloqueos para que miles de usuarios lean/escriban a la vez sin corromper datos.
  • Recuperación: Backups y logs para restaurar el sistema tras una caída o fallo eléctrico.
¿Qué son las siglas ACID en una Base de Datos?

Las bases de datos relacionales garantizan la fiabilidad de las operaciones mediante cuatro propiedades fundamentales agrupadas bajo las siglas ACID:

A - Atomicidad

"Todo o nada". Una transacción se ejecuta por completo o falla por completo. Si se cae la luz a mitad de una transferencia bancaria, no se descuenta el dinero sin haberlo ingresado en la otra cuenta.

C - Consistencia

Asegura que la base de datos pase de un estado válido a otro estado válido, cumpliendo siempre las reglas y restricciones (ej. que una cuenta no pueda quedar con saldo negativo si la regla lo prohíbe).

I - Aislamiento (Isolation)

Varias transacciones ocurriendo a la vez no interfieren entre sí. El resultado de ejecutar dos operaciones a la vez debe ser el mismo que si se ejecutaran una tras otra.

D - Durabilidad

Una vez que el SGBD confirma que la transacción ha sido exitosa (commit), los cambios son permanentes y no se perderán, incluso si el servidor sufre un apagón inmediatamente después.

4. Arquitectura y Elementos de un SGBD

Internamente, un SGBD es un software muy complejo dividido en varios componentes o capas (elementos funcionales):

Procesador de Consultas

Recibe las instrucciones SQL, las analiza (parser) y decide el plan de ejecución más óptimo para devolver resultados rápido.

Gestor de Almacenamiento

Controla el acceso al disco del Sistema Operativo, guardando las tablas e índices en bloques de ficheros físicos.

Gestor de Transacciones

Garantiza las propiedades ACID. Se encarga de los bloqueos de concurrencia y la escritura del log de recuperación.

Diccionario de Datos

Contiene los "Metadatos": descripciones de todas las tablas, columnas, tipos de datos y permisos existentes.

El Lenguaje SQL (Sublenguajes)

El lenguaje SQL es la interfaz estándar mediante la cual nos comunicamos con cualquier SGBD relacional. Según la función que queramos realizar, sus comandos se dividen en cuatro sublenguajes:

DDL

Data Definition Language

Sirve para definir y modificar la estructura de la base de datos (crear, borrar o alterar tablas y esquemas).

CREATE, DROP, ALTER

DML

Data Manipulation Language

Se utiliza para interactuar con los datos (consultar, insertar, modificar o borrar registros existentes).

SELECT, INSERT, UPDATE, DELETE

DCL

Data Control Language

Instrucciones para la seguridad y el control de accesos (dar o quitar permisos a los usuarios).

GRANT, REVOKE

TCL

Transaction Control Language

Manejo de transacciones para confirmar o deshacer bloques de operaciones y asegurar las propiedades ACID.

COMMIT, ROLLBACK

5. Clasificación de SGBD (Mercado)

SGBD Libres / Open Source

Su código es público. Tienen un inmenso soporte comunitario y no requieren pago por licencia base.

  • MySQL: Históricamente el más usado en desarrollo web (LAMP). Hoy propiedad de Oracle.
  • MariaDB: Fork (bifurcación) 100% libre creado por la comunidad cuando MySQL fue comprado.
  • PostgreSQL: El motor libre más robusto y avanzado, ideal para bases de datos complejas.
SGBD Propietarios (Comerciales)

Líderes históricos en el mundo corporativo. Requieren licencias costosas pero ofrecen ecosistemas cerrados muy potentes.

  • Oracle Database: El pionero y estándar en grandes corporaciones (Bancos, Seguros).
  • Microsoft SQL Server: Muy integrado con el ecosistema Windows y Azure.

6. Ubicación: Centralizadas vs Distribuidas

Las bases de datos se clasifican también en función de cómo se reparte su arquitectura física y de red a través de los servidores:

Sistemas Centralizados

Todos los datos, el motor SGBD y el procesamiento ocurren en un único servidor principal (o mainframe).

  • Ventajas: Mantenimiento simple, control de seguridad en un solo punto, operaciones muy rápidas al no depender de la red externa.
  • Inconvenientes: "Punto único de fallo". Si el servidor se apaga o se rompe el disco, el sistema entero se cae. Cuellos de botella si hay muchos usuarios a la vez.
Ejemplo del mundo real:

El sistema de gestión del inventario de una farmacia local, o el servidor de matriculaciones de un instituto pequeño, donde una sola torre de ordenador en la trastienda aloja todos los datos con MySQL.

Bases de Datos Distribuidas

Los datos se reparten o replican en múltiples servidores físicos (nodos) interconectados por red, aunque para el usuario final parece ser una única base de datos central.

  • Ventajas: Alta disponibilidad (si cae un nodo, responden los demás), escalabilidad enorme (se añaden más servidores), velocidad global (los datos están físicamente más cerca del usuario).
  • Inconvenientes: Muy complejas de configurar, caras, y sufren latencia de red para mantener todo sincronizado (consenso).
Ejemplos del mundo real:

Netflix usa Apache Cassandra distribuido globalmente: tu cuenta existe tanto en servidores de Europa como de EE.UU. para que siempre cargue rápido estés donde estés. WhatsApp usa bases de datos distribuidas para manejar millones de mensajes sin caerse nunca.

Ventajas Distribuidas
  • Alta disponibilidad: Si cae un servidor (nodo), la BD sigue funcionando con el resto.
  • Escalabilidad horizontal: Se pueden añadir más ordenadores baratos al clúster si se necesita más potencia.
  • Proximidad: Los datos se acercan geográficamente al usuario (mejor latencia).
Desventajas Distribuidas
  • Complejidad extrema: Garantizar que todos los nodos vean el mismo dato a la vez (consistencia y replicación) es muy complejo.
  • Seguridad de red: Los nodos deben intercambiar datos cifrados por internet.
  • Velocidad de escritura: Las transacciones lentifican la red porque deben confirmarse en varios nodos.
El problema de la cena de los filósofos

Es un problema clásico propuesto por Edsger Dijkstra para representar los retos de sincronización (concurrencia) en sistemas como los SGBD.

Imagina a 5 filósofos sentados en una mesa redonda. Tienen un plato de arroz, pero solo hay 5 palillos en total (uno entre cada filósofo).

Para comer, un filósofo necesita dos palillos (el de su izquierda y el de su derecha). Si todos los filósofos deciden comer exactamente al mismo tiempo y cada uno coge el palillo de su derecha, todos se quedarán esperando infinitamente a que el otro suelte su palillo izquierdo.

Esto se llama Interbloqueo (Deadlock).

En Bases de Datos: Los filósofos son los usuarios intentando leer/escribir y los palillos son los datos. El SGBD aplica algoritmos para evitar que la base de datos se quede bloqueada para siempre, decidiendo quién coge el dato primero.

Transacciones: Guardar la partida

El concepto de Transacción es vital en las Bases de Datos para garantizar que la información no se corrompa si algo falla a medias.

Jefe Final

Imagina que estás jugando a un videojuego y vas a enfrentarte al monstruo final.

  • START TRANSACTION: Decides Guardar la Partida antes de cruzar la puerta.
  • A partir de ahí empiezas a luchar (insertar, borrar, actualizar datos en la BBDD).
  • COMMIT: Si vences al jefe, guardas la partida de nuevo. Tus progresos (y tus datos) se hacen permanentes.
  • ROLLBACK: Si el jefe te elimina (o hay un error de red en la BBDD), el sistema carga automáticamente la partida guardada. ¡Vuelves al punto inicial sin perder nada!

Así el SGBD garantiza que una transferencia bancaria no descuente el dinero de tu cuenta si luego falla al ingresarlo en la otra. O se hace todo (COMMIT), o no se hace nada (ROLLBACK).

Abstracción: Conducir un coche

Piensa en cómo conduces un coche. Tú solo necesitas saber usar el volante, los pedales y la palanca de cambios.

No necesitas saber cómo funciona la inyección de combustible en el motor, ni cómo los engranajes de la caja de cambios se acoplan físicamente. El coche abstrae toda esa complejidad mecánica y te ofrece una interfaz sencilla (los pedales).

En Bases de Datos: El SGBD es el coche. Tú usas el "volante" (comandos SQL como SELECT) y el SGBD se encarga de la complejidad de buscar los datos en los cilindros físicos del disco duro.

Integridad: El portero de discoteca

Imagina un portero estricto en la puerta de un club nocturno. Tiene unas reglas muy claras establecidas por el dueño.

Si la regla dice "Solo mayores de 18", el portero pide el DNI. Si tienes 17, no pasas. No hay excepciones ni errores posibles. Él garantiza que dentro del club solo haya gente que cumpla las normas.

En Bases de Datos: El SGBD es el portero. Si tú defines que una columna "Edad" debe ser un número entero mayor que 0, y alguien intenta guardar el texto "Veinte", el SGBD lo rechazará instantáneamente protegiendo la integridad de tus datos.

Seguridad: Llaves magnéticas de hotel

Cuando te alojas en un hotel grande, te dan una tarjeta magnética configurada específicamente para ti.

Tu tarjeta abre la puerta principal y la puerta de tu habitación (rol de cliente). Sin embargo, la tarjeta del personal de limpieza abre todas las habitaciones (rol de mantenimiento), y la del director abre hasta la caja fuerte (rol administrador).

En Bases de Datos: El SGBD permite crear usuarios con diferentes niveles de privilegios (tarjetas). Un usuario normal solo podrá hacer SELECT en ciertas tablas, mientras que el administrador (DBA) podrá borrar o modificar estructuras.

Recuperación: La caja negra del avión

Todos los aviones comerciales llevan instalada una caja negra (Flight Data Recorder).

Este dispositivo es indestructible y va grabando meticulosamente cada acción del piloto, cada cambio de altitud y cada parámetro del motor milisegundo a milisegundo. Si ocurre un accidente fatal, los ingenieros pueden leer la caja negra y reconstruir exactamente qué pasó.

En Bases de Datos: El SGBD guarda una caja negra llamada Transaction Log (Registro de transacciones). Si se va la luz mientras se guardaban datos y los ficheros se corrompen, el motor lee el log al arrancar y es capaz de reconstruir y recuperar la base de datos hasta el último milisegundo válido.
