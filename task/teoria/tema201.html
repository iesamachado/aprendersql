1. Tipos de SGBD (Sistemas Gestores de Bases de Datos)

Los SGBD se pueden clasificar principalmente en dos grandes categorías, dependiendo de su modelo de datos y características relacionales:

Utilizan el modelo relacional donde los datos se almacenan en tablas (filas y columnas) vinculadas mediante claves. Ejemplos: MySQL, MariaDB, PostgreSQL, Oracle, SQL Server.

No utilizan el modelo tabular clásico, diseñados para grandes volúmenes de datos distribuidos. Tipos: Documentales (MongoDB), Clave-Valor (Redis), Grafos (Neo4j), Columnas (Cassandra).

2. Arquitectura ANSI/SPARC

La arquitectura ANSI/SPARC de tres niveles es un estándar para el diseño de SGBD, que separa la visión del usuario de la estructura física de la base de datos:

  • Nivel Externo (Vistas): Es la forma en que los usuarios o aplicaciones ven los datos. Permite múltiples vistas personalizadas.
  • Nivel Conceptual (Lógico): Describe qué datos se almacenan en la base de datos y las relaciones entre ellos (tablas, restricciones), ocultando los detalles físicos.
  • Nivel Interno (Físico): Describe cómo se almacenan físicamente los datos en los dispositivos de almacenamiento (índices, archivos, asignación de espacio).

Ventaja principal: Independencia de datos (lógica y física).

3. El Diccionario de Datos (information_schema)

El Diccionario de Datos (o Catálogo del Sistema) es una base de datos especial que el propio SGBD mantiene de forma automática. Contiene metadatos: datos sobre los propios datos. Saber leerlo es una habilidad esencial de cualquier administrador.

Analogía: Si tu base de datos es una biblioteca, el diccionario de datos es el catálogo del bibliotecario: sabe exactamente qué libros hay, en qué estantería están, cuánto pesan y quién tiene permiso para leerlos.

En MariaDB, el diccionario de datos se accede a través de la base de datos virtual information_schema. No ocupa espacio en disco: se genera en memoria en el momento de la consulta.

Vistas más importantes de information_schema

Vista¿Qué contiene?Ejemplo de uso
TABLESTodas las tablas de todas las BDs: nombre, motor, número de filas, tamaño...Ver qué tablas tiene una BD
COLUMNSTodas las columnas de todas las tablas: nombre, tipo de dato, nulabilidad, valor por defecto...Auditar si una columna existe en producción
ROUTINESFunciones y procedimientos almacenados: nombre, parámetros, cuerpo del código...Listar todos los procedimientos de una BD
TRIGGERSTodos los triggers: evento (INSERT/UPDATE), tabla asociada, cuerpo...Ver qué triggers pueden estar disparándose
VIEWSTodas las vistas: definición de la consulta SQL que las generaRevisar si una vista está bien definida
USER_PRIVILEGESPrivilegios globales de los usuariosAuditoría de seguridad

Consultas útiles de administración

SELECT
  TABLE_NAME          AS 'Tabla',
  ENGINE              AS 'Motor',
  TABLE_ROWS          AS 'Filas (aprox)',
  ROUND(DATA_LENGTH / 1024 / 1024, 2) AS 'Tamaño (MB)'
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'arepazo'
ORDER BY DATA_LENGTH DESC;

SELECT
  COLUMN_NAME    AS 'Columna',
  DATA_TYPE      AS 'Tipo',
  IS_NULLABLE    AS 'Nulable',
  COLUMN_DEFAULT AS 'Valor por defecto'
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = 'arepazo'
  AND TABLE_NAME   = 'pedidos'
ORDER BY ORDINAL_POSITION;

SELECT
  ROUTINE_NAME AS 'Nombre',
  ROUTINE_TYPE AS 'Tipo',    -- PROCEDURE o FUNCTION
  DATA_TYPE    AS 'Devuelve'
FROM information_schema.ROUTINES
WHERE ROUTINE_SCHEMA = 'arepazo';

SELECT
  TRIGGER_NAME   AS 'Trigger',
  EVENT_MANIPULATION AS 'Evento',   -- INSERT, UPDATE, DELETE
  EVENT_OBJECT_TABLE AS 'Sobre tabla',
  ACTION_TIMING  AS 'BEFORE/AFTER'
FROM information_schema.TRIGGERS
WHERE TRIGGER_SCHEMA = 'arepazo';
Seguridad: Los usuarios solo ven en information_schema los objetos sobre los que tienen permisos. Un usuario con acceso solo a una tabla no podrá ver la definición de las demás. Esto lo convierte también en una herramienta de auditoría de permisos.

3. Instalación usando Docker

Docker es una herramienta que nos permite "virtualizar" varias bases de datos en un mismo equipo utilizando contenedores ligeros en lugar de máquinas virtuales completas.

  • Un contenedor por servicio.
  • Podremos tener varios SGBD (MySQL, SQL Server) en la misma máquina funcionando en puertos distintos.
  • Es más ágil de levantar y consume menos recursos que VirtualBox.

3.1. MariaDB en Linux / Docker

MariaDB es un SGBD libre con licencia GPL, muy usado en entornos web (LAMP o XAMP).

Para levantar MariaDB con Docker exponiendo el puerto 3306 y configurando la contraseña root, y utilizando un volumen persistente:


docker run -d --name mariadb_server \
  -e MYSQL_ROOT_PASSWORD=root \
  -p 3306:3306 \
  -v mariadb_data:/var/lib/mysql \
  mariadb:latest

También podemos usar Docker Compose creando un archivo docker-compose.yml y ejecutando docker-compose up -d.

Configuración adicional de MariaDB (Nativo en Linux)

Si se instala nativamente con apt install mariadb-server, se recomienda ejecutar:

sudo mysql_secure_installation

Para permitir conexiones remotas, editar /etc/mysql/mariadb.conf.d/50-server.cnf y comentar la línea bind-address, luego reiniciar: sudo systemctl restart mariadb.

4. Oracle en Oracle Cloud / Linux

Oracle Database es un SGBD relacional avanzado. Instalarlo localmente puede ser pesado, por lo que una excelente opción es desplegarlo en Oracle Cloud usando una instancia de Linux.

  1. Crear una instancia "Always Free" de Compute (ej. Oracle Linux) en Oracle Cloud.
  2. Configurar las reglas de ingreso (Ingress Rules) en la red virtual (VCN) para abrir el puerto de escucha (por defecto 1521).
  3. Acceder por SSH a la máquina Linux e instalar los pre-requisitos de Oracle o utilizar una imagen de Docker de Oracle Database preconfigurada.
  4. Si se usa Docker para Oracle Database 21c/19c Express Edition (XE): 
    docker run -d --name oracle_db \
  -p 1521:1521 -p 5500:5500 \
  -e ORACLE_PWD=TuPasswordSeguro123 \
  -e ORACLE_CHARACTERSET=AL32UTF8 \
  container-registry.oracle.com/database/express:latest
  5. Conectarse remotamente utilizando un cliente como SQL Developer.

5. SQL Server en VirtualBox con Windows

Para instalar Microsoft SQL Server en un entorno aislado usando VirtualBox:

  1. Preparar Máquina Virtual: Instalar Windows (10/11 o Windows Server) en VirtualBox. Asignar al menos 4GB de RAM y configuración de red en modo "Adaptador Puente" para tener IP propia en la red local.
  2. Descargar Instalador: Descargar SQL Server 2019/2022 Developer Edition (gratuita para desarrollo y pruebas).
  3. Ejecutar Centro de Instalación: Seleccionar "Nueva instalación independiente de SQL Server".
  4. Selección de características: Seleccionar "Servicios de Motor de base de datos" (Database Engine Services).
  5. Configuración de Instancia: Se puede elegir "Instancia predeterminada" (MSSQLSERVER).
  6. Configuración del Servidor: En "Modo de autenticación", elegir Modo mixto (Autenticación de SQL Server y de Windows). Esto es crucial para poder conectarse con el usuario sa (System Administrator). Introducir una contraseña segura para sa.
  7. Habilitar Conexiones Remotas:
    • Abrir "Administrador de configuración de SQL Server" (SQL Server Configuration Manager).
    • Ir a "Configuración de red de SQL Server" -> "Protocolos de MSSQLSERVER".
    • Habilitar el protocolo TCP/IP.
    • Reiniciar el servicio de SQL Server desde la propia herramienta.
  8. Firewall: Desactivar el Firewall de Windows en la máquina virtual, o añadir una regla de entrada para permitir el tráfico en el puerto TCP 1433.
